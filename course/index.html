Chapter 1

What is a language model?

By the end of this chapter you can explain:
  • what a language model does, in one sentence
  • what "a model" physically is on a computer
  • why a model sometimes makes things up

Start with a game you already play

Finish this sentence: "The students opened their ___."

You probably thought of "books" or "laptops". You did not think of "volcano". Without any effort you ranked the possible next words by how likely they are.

That is the entire job of a language model. You give it some text. It gives back its best guess for what comes next, with a probability for each candidate. Everything else you have seen ChatGPT or Claude do is built on top of this one trick.

Try it: be the language model (the percentages are made up for teaching)

Click a word to add it to the sentence. Watch the choices change each time.

Teacher's note

Notice two things. First, the model never "decides what it wants to say". It only scores possible next words. Second, when it picks one, that word is added to the text and the whole thing is fed back in to get the next word. A long answer is just this loop repeated hundreds of times. Press "Let the model pick" a few times and you will see it.

Words are really "tokens"

Strictly speaking, models do not read whole words. They read tokens, which are small pieces of text. A common word like "books" is usually one token. A rare or long word may be split into several pieces. Each piece is given an ID number, and the model works with the numbers. For now, when you read "word", think "token". We will keep saying "word" because it is easier.

What is a "model", physically?

This surprises almost everyone. A model such as Meta's Llama 2 70B, an open model whose details were published, is just two files on a computer:

  1. A parameters file. A very long list of numbers. These numbers are the "knowledge" of the model.
  2. A small program. It takes your text and those numbers and calculates the next-word probabilities. For this model, the program is only about 500 lines of code.

The "70B" means 70 billion parameters. Each one is stored in 2 bytes. So the size is easy to calculate yourself:

Calculator: how big is the parameters file?
parameters140 GB
run program~500 linesof plain code, no internet needed

With those two files on a laptop, you could run the model with no internet connection. The program is simple and well understood. All the magic is in the numbers. The next chapter explains where the numbers come from.

Why does predicting words make a model smart?

Imagine the model reads a Wikipedia article about a famous inventor and has to guess the next word at every position. To guess well, it needs to know when she was born, what she invented, and who she worked with. Nobody wrote these facts into the model. The model absorbed them because they help it predict. A simple-sounding goal forces the model to learn a lot about the world, and it stores that learning in its parameters.

You can think of the parameters as a blurry zip file of the internet. Unlike a real zip file, it is lossy: you get the gist of the text, not an exact copy.

Why it sometimes makes things up (hallucination)

Because the model is a blurry memory that fills in plausible words, it sometimes writes something that sounds right and is false. This is called a hallucination. A classic example is asking it for a book's ISBN number. The model knows an ISBN looks like a number of a certain length, so it produces a number of that shape. It may not exist.

Remember this

A language model produces the most plausible text, not the most true text. Most of what you will learn in this course (retrieval, tools, evaluation, agents) exists to close the gap between plausible and true.

One more oddity. Researchers do not fully understand what each of the billions of numbers does. We can measure that the model gets better at predicting, but we cannot point at a number and say "this one stores the capital of France". So we treat models like something we test by experiment: give it inputs, look at outputs, and measure how often it is right. This is why evaluation gets its own chapter later.

Chapter 1 in plain words

  • A language model predicts the next token, over and over.
  • The model is a big file of numbers plus a small program.
  • Learning to predict forces it to absorb knowledge, but only as a blurry memory.
  • So it can state false things confidently (hallucination).

Chapter 2

How a language model is made

By the end of this chapter you can explain:
  • the difference between a "base model" and an "assistant"
  • what pre-training, fine-tuning and human feedback each do
  • why companies only pre-train rarely but fine-tune often

The learning loop in three words: guess, compare, nudge

Where do the billions of numbers come from? From training. Picture the model as a student doing a huge fill-in-the-blank exercise:

1. GuessShow the model some text with the last word hidden. It guesses the probabilities.
→
2. CompareCheck the real next word. Did the model give it a high probability?
→
3. NudgeAdjust the numbers slightly so the real word would have scored higher.

Repeat this for a gigantic amount of text and the numbers slowly settle into a useful state. No human tells the model what any individual number should be. The only instruction is "get better at predicting".

Two big stages (and one optional)

Click through the stages. Each one uses the same guess, compare, nudge loop. What changes is the data.

The assembly line

Base model versus assistant: why we need stage 2

After stage 1 you have a base model. It is an expert at continuing internet text, and nothing else. Ask it a question and it may continue with more questions, because a list of questions is a very normal thing to find on the internet. Stage 2 teaches it a new habit: when a user asks something, reply like a helpful assistant.

Base model (after stage 1)

You: What is the capital of France?
Model: What is the capital of Germany? What is the capital of Spain? What is…

Assistant (after stage 2)

You: What is the capital of France?
Model: The capital of France is Paris.

This pair is an illustration of the behaviour, not a recording of a real model.

Here is the neat part. The 100,000 or so example conversations are tiny compared with the internet, but they are enough. The model's knowledge from stage 1 stays; stage 2 only changes the style of how it answers. Pre-training is about knowledge. Fine-tuning is about behaviour, which people also call alignment.

Stage 3: learning from comparisons

Writing a perfect answer from scratch is hard. Picking the better of two answers is much easier. Companies use this fact to improve models further. It is called RLHF. Try being the labeler:

Be a labeler Task: "Write a haiku about paper clips."

Answer A

Bent silver ribbon,
holding pages together,
quiet desk helper.

Answer B

Paper clips are good,
they hold the papers so well,
I like paper clips.

Why cost and frequency differ so much

The numbers below describe Llama 2 70B, an older model whose training details were published. Today's best models cost ten times more or beyond, which means tens or even hundreds of millions of dollars.

Stage 1 versus stage 2

Pre-training

  • About 10 terabytes of text
  • About 6,000 GPUs for about 12 days
  • Roughly $2 million
  • Done rarely: once every few months or a year

Fine-tuning

  • About 100,000 quality conversations
  • Hours to about a day of computing
  • Much cheaper
  • Repeated often: weekly, even daily

Companies improve their assistants in a loop. Deploy, watch for bad answers, have a person write the correct answer for each bad case, add it to the fine-tuning data, and train again. Because fine-tuning is cheap, this loop runs quickly.

Open models and closed models

Some companies, like Meta with Llama, release the parameters file so anyone can run or fine-tune the model. These are called open-weights models. Others, like OpenAI and Anthropic, keep the weights private and let you use the model through a website or an API. Closed models have usually been stronger, and open ones are catching up. Which one is right depends on your task.

One more idea: scaling

Researchers found that how well a model predicts the next word depends mainly on two things: how many parameters it has and how much text it was trained on. Make both larger and it reliably gets better, without needing new inventions. That is why companies are racing to get more computers and more data.

Chapter 2 in plain words

  • Training is guess, compare, nudge, repeated at enormous scale.
  • Stage 1 (pre-training) on internet text gives knowledge: a base model.
  • Stage 2 (fine-tuning) on human-written conversations gives helpful behaviour: an assistant.
  • Stage 3 (RLHF) uses human comparisons to polish answers.
  • Stage 1 is rare and costly. Stages 2 and 3 are quick and repeated.

Chapter 3

Talking to a model: prompting

By the end of this chapter you can:
  • explain what an API call to a model looks like
  • use five habits that improve any prompt
  • describe why measuring results matters from day one

How software talks to a model

When you use a chat website, you type text and get text back. Programs do the same through an API:

Your softwareBuilds the text of a request
→
Model providerRuns the model on powerful computers
→
Generated textReturns to your software
→
Your softwareReads the text and uses it, or sends another request

The input is free-form text, written in ordinary language. The text you send is called a prompt. Writing it well is called prompting, and it is the single biggest lever you have. The same model can give a poor or an excellent answer depending on the prompt.

Five habits of good prompts

Habit 1: be clear and detailed

The model cannot read your mind. "Write about our bottle" leaves it guessing the length, the audience, the tone and the facts. Say what you want.

Habit 2: show examples

Give one or two sample inputs and outputs in the style you want, then ask your real question. This is called few-shot prompting. Showing is often stronger than describing.

Habit 3: give it the facts

If the answer depends on specific information, paste that information in, and tell the model to use only that. Add "if the answer is not in the text, say you cannot find it". This cuts down hallucination a lot, and it is the seed of the technique in Chapter 4.

Habit 4: let it think before it answers

Asking for the answer immediately gives the model no room to work. Ask it to reason first. This is called chain of thought. A well-known case: ask a mid-sized model "is this student's maths solution correct?" and it may just agree. Ask it to first work out its own solution, then compare, and it checks properly. The written steps are part of the text the model reads when it produces the next words, so they genuinely help.

Habit 5: split big jobs into small steps

One prompt with five tasks often goes badly. Five prompts with one task each, where the output of each feeds the next, works better. This is called prompt chaining.

Prompt 1Extract the key facts
→
Prompt 2Outline using those facts
→
Prompt 3Write the final text from the outline
Prompt lab Tick habits and watch the prompt grow

Your prompt:

Two engineering habits that beginners skip

  • Keep logs. Record the prompts you sent and the answers you got. When something goes wrong, the log is how you find out why.
  • Measure from the start. Make a small set of questions with the answers you expect, and score your system against it each time you change something. Humans can do the scoring, but that is slow and costly, so people often ask a second model to grade the answers. That is called LLM-as-a-judge. Models improve and get retired quickly. If you can measure, you can switch to a better model with confidence.

A cost-saving trick: the router

Not every question needs the biggest model. A small piece of software (or a small model) can look at each incoming request and send it to the right prompt and the right model. Simple questions go to a cheap model. Hard ones go to a strong model. This lowers cost and often improves quality.

Chapter 3 in plain words

  • Software talks to a model by sending text and reading text back.
  • Good prompts are clear, show examples, supply facts, allow thinking and split big jobs.
  • Keep logs and measure results from the first day.
  • A router can send easy requests to cheap models.

Chapter 4

Fixing a model's weaknesses

By the end of this chapter you can explain:
  • five common weaknesses of language models
  • how retrieval-augmented generation (RAG) works, step by step
  • how tool use (function calling) lets a model act on the world

Five weaknesses

Even a strong model has limits. Knowing them tells you why the techniques in this chapter exist.

  1. Hallucination. It can state false things confidently, especially in maths and specific facts.
  2. Knowledge cut-off. Its training data stops at some date. It has not seen recent news.
  3. No sources. It can answer, but it cannot tell you which document the answer came from.
  4. No private data. It was trained on public text. It has never seen your company's documents.
  5. Limited context. It can only read so much text at once. Longer inputs cost more and respond slower.

Fix 1: Retrieval-Augmented Generation (RAG)

The idea is simple. Do not ask the model to remember. Look up the relevant pages first, then hand them to the model with the question. It is an open-book exam instead of a closed-book exam. You already used the prompt side of this in Chapter 3, habit 3. RAG adds the automatic "look up" step.

RAG step by step Example: a company help desk
Words you will hear

Chunk: a small piece of a document, like one paragraph. Embedding: a list of numbers that represents the meaning of a piece of text, so texts with similar meaning get similar numbers. Vector database: a store that can quickly find the stored chunks whose numbers are closest to a question's numbers. Top-k: the k best matches, for example the best 3.

There are other ways to retrieve. You can search the web instead of your own files. You can also turn your documents into a knowledge graph (things and the relationships between them), which is called graph RAG. The common pattern is the same: find relevant material, put it in the prompt.

What RAG fixes

  • Less hallucination, because the answer comes from supplied text.
  • Citations are possible, because you know which chunk was used.
  • Your private documents become usable.
  • You only send a few relevant chunks, so the context stays short.

Fix 2: Tool use (function calling)

A language model takes text in and gives text out. On its own it cannot check the weather, send an email or run a calculation reliably. Tool use gives it hands.

You tell the model, in the prompt, which tools exist and the exact format to use when it wants one. When the model decides a tool is needed, it writes a request in that format. Your software (not the model) notices the request, runs the real function, and passes the result back to the model. Then the model writes the final answer for the user. Step through it:

Tool use step by step Question: "What's the weather in San Francisco?"

Common mistake

Beginners think the model itself calls the weather service. It does not. The model only writes text that asks for the call. Your own program does the calling. This split matters a lot for safety, because your software decides what is allowed to run.

The same idea covers writing code. The model can write a small program to do a calculation or draw a chart, and your software runs it in a protected area called a sandbox, then returns the output to the model.

Where this leads

Put the pieces together. A model that can retrieve information, use tools, and look at the results and decide what to do next is no longer just answering. It is working on a task. That is the starting point for the next chapter, where we meet AI agents.

Chapter 4 in plain words

  • Models hallucinate, go out of date, cite nothing, miss private data and have limited reading room.
  • RAG looks up relevant chunks and puts them into the prompt.
  • Tool use lets the model ask your software to run functions and return results.
  • Combine retrieval, tools and a loop, and you are close to an agent.

Glossary

Language model (LLM)
A program that predicts the next token in a piece of text. "LLM" means large language model.
Token
A small piece of text, often a word or part of one, that the model treats as one unit.
Parameters (weights)
The billions of numbers inside a model that store what it learned.
Pre-training
Stage 1: learning to predict the next token from a huge amount of internet text.
Fine-tuning
Stage 2: training on a smaller set of high-quality example conversations so the model behaves like an assistant.
RLHF
Using human comparisons of answers to improve a model further.
Hallucination
A confident answer that is not true.
Prompt
The text you send to a model.
Few-shot prompting
Including a few examples in the prompt.
Chain of thought
Asking the model to reason in steps before answering.
Prompt chaining
Splitting a task into a series of simple prompts.
LLM-as-a-judge
Using a model to score the outputs of another model.
API
A way for programs to send requests to each other and receive answers.
RAG
Retrieval-Augmented Generation: look up relevant text and give it to the model with the question.
Embedding
A list of numbers that captures the meaning of a text, used to find similar texts.
Tool use / function calling
The model writes a structured request, your software runs it and returns the result.
Sandbox
A protected place where generated code can run safely.
