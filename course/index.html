What is a language model?

Start with a game you already play

Finish this sentence: "The students opened their ___."

You probably thought of "books" or "laptops". You did not think of "volcano". Without any effort you ranked the possible next words by how likely they are.

That is the entire job of a language model. You give it some text. It gives back its best guess for what comes next, with a probability for each candidate. Everything else you have seen ChatGPT or Claude do is built on top of this one trick.

Where does a language model sit?

People throw around many names. Here is how they nest, from the biggest idea to the smallest.

  • Artificial intelligence (AI) is the broad goal: software that does things we associate with intelligence.
  • Machine learning is one way to get there. Instead of writing rules by hand, you let the computer find patterns in data.
  • Deep learning is machine learning that uses neural networks with many layers.
  • A Transformer is a particular design of neural network that is very good at sequences like text.
  • A large language model (LLM) is a Transformer-style model trained at huge scale on text. GPT, Claude, Gemini and Llama are examples.
Teacher says

Do not just memorise the nesting. Ask what each box adds. Machine learning adds "learn from data". Neural networks add a flexible function that can be tuned. Transformers add a strong way to handle sequences. Large-scale training adds broad language ability.

Student asks

If ChatGPT is an LLM, is it "just the Transformer"?

No. The Transformer is the model design. A product like a chat assistant also has an interface, hidden system instructions, safety filters, often retrieval and tools, memory, and monitoring. The model is the engine. The product is the whole car. This matters later, because an agent is also "model plus a lot of software around it".

Words are really "tokens"

Strictly speaking, models do not read whole words. They read tokens, which are small pieces of text. A common word like "books" is usually one token. A rare or long word may be split into several pieces. Each piece is given an ID number, and the model works with the numbers. For now, when you read "word", think "token". Chapter 2 opens up the tokenizer and shows how the pieces are chosen.

What is a "model", physically?

This surprises almost everyone. A model such as Meta's Llama 2 70B, an open model whose details were published, is just two files on a computer:

  1. A parameters file. A very long list of numbers. These numbers are the "knowledge" of the model.
  2. A small program. It takes your text and those numbers and calculates the next-word probabilities. For this model, the program is only about 500 lines of code.

The "70B" means 70 billion parameters. Each one is stored in 2 bytes. So the size is easy to calculate yourself:

With those two files on a laptop, you could run the model with no internet connection. The program is simple and well understood. All the magic is in the numbers. Chapter 3 explains where the numbers come from.

Why does predicting words make a model smart?

Imagine the model reads a Wikipedia article about a famous inventor and has to guess the next word at every position. To guess well, it needs to know when she was born, what she invented, and who she worked with. Nobody wrote these facts into the model. The model absorbed them because they help it predict. A simple-sounding goal forces the model to learn a lot about the world, and it stores that learning in its parameters.

You can think of the parameters as a blurry zip file of the internet. Unlike a real zip file, it is lossy: you get the gist of the text, not an exact copy.

Why it sometimes makes things up (hallucination)

Because the model is a blurry memory that fills in plausible words, it sometimes writes something that sounds right and is false. This is called a hallucination. A classic example is asking it for a book's ISBN number. The model knows an ISBN looks like a number of a certain length, so it produces a number of that shape. It may not exist.

Remember this

A language model produces the most plausible text, not the most true text. In engineering terms: a fluent answer is not a verified fact. When the answer matters, you show evidence, use a tool, retrieve documentation, or verify. Most of this course (retrieval, tools, evaluation, agents) exists to close the gap between plausible and true.

One more oddity. Researchers do not fully understand what each of the billions of numbers does. We know every mathematical operation the model performs, yet we cannot point at one number and say "this one stores the capital of France". The knowledge can even be lopsided. A famous example: a model can answer "Who is Tom Cruise's mother?" correctly but fail to answer "Who is that woman's son?". So we treat models as things we test by experiment: give inputs, look at outputs, and measure how often they are right. This is why evaluation gets its own chapters later.

A neural network is a function made of numbers

A neural network takes numbers in, passes them through layers, and gives numbers out. Training adjusts its parameters so the outputs get better at some goal. The word "neural" is only loosely inspired by brain cells. A single artificial neuron is just arithmetic:

output = activation( w1×x1 + w2×x2 + bias )

The weights (w) and the bias are the learned numbers. The activation is a small bend that stops the neuron being a plain straight-line calculation. Without the bend, stacking layers would add nothing. Try it:

One neuron Move the sliders and watch the output

A large language model is this idea scaled up: billions of weights arranged in many layers. You do not need more calculus than that to build agents. But you should hold on to one fact: an LLM is not a database or a rules engine. It is a giant learned function whose behaviour comes from many layers of numerical transformations.

Step 1: Tokenization (text becomes numbers)

A computer cannot feed an English sentence into a neural network. A tokenizer first cuts the text into pieces and gives each piece an ID number. Why not simply use whole words? Two reasons:

  • Typos and rare words. If every word is its own token, a misspelling or a new name has no token at all. Some languages (Thai, for example) do not even put spaces between words.
  • The other extreme fails too. Splitting into single letters works, but sequences become very long. The cost of attention (below) grows roughly with the square of the sequence length, so long sequences are expensive.

The compromise is sub-word tokens: common chunks of letters become one token, rarer words are assembled from pieces. On average a token is about 3 to 4 letters. A popular recipe is byte-pair encoding. You can run its training steps yourself on a tiny text:

Build a tokenizer Corpus: token ×3, tokens ×2, tokenizer ×2, to ×2, toe ×1

Start with single letters. At each step, find the most frequent neighbouring pair and merge it into a new token.

Why you care

The number of tokens drives cost, speed and how much fits in memory. An agent that pastes every raw log line into every model call wastes tokens. Tokenization also explains odd behaviour: models handle numbers and code indentation differently from how people do, because numbers and spaces were chopped up in particular ways. (GPT-4 changed how it tokenizes code spaces and got better at code.)

Step 2: Embeddings (IDs become meaningful vectors)

A token ID is just an index, like a locker number. The number 431 tells the model nothing about meaning. So each ID is looked up in a table that returns a list of numbers called an embedding. During training, the table is adjusted so that tokens used in similar ways get similar vectors.

Real embeddings have hundreds or thousands of numbers. We can only draw two. In the map below (invented positions, for teaching), things with similar meaning sit near each other. The dot product and its cousin cosine similarity measure how well two arrows line up. They are the basic similarity tool of both attention and search.

Student asks

Does an embedding store the definition of a word?

No. It is a learned vector, not a dictionary entry. Meaning is spread across the numbers, and it changes with context as the vector passes through the Transformer layers. For example, "bank" has the same token ID whether it means a money bank or a river bank. The layers adjust the representation using the surrounding words.

Embeddings are also used outside the model. A document chunk and a user question can both be turned into vectors and compared. This is the foundation of semantic search and RAG, which you will meet in Chapter 6.

Step 3: Position (order matters)

"Dog bites man" and "man bites dog" use the same words with very different meaning. Attention by itself looks at a bag of tokens, so the model also adds information about where each token sits. Each token's representation therefore carries two things: what token it is and where it is in the sequence. Different models encode position in different ways. The engineering idea matters more than the exact formula.

Step 4: Self-attention (tokens look at each other)

Take the sentence "The cat, which was hungry, ate the fish." When the model processes "ate", which other words matter most? "cat" (who ate?), "fish" (what was eaten?), and probably "hungry". "The" matters much less. Self-attention is the mechanism that lets each token build a richer representation by mixing in information from the others, weighted by relevance.

Each token produces three vectors, which you can remember with a library analogy:

  • Query (Q): "what am I looking for?" (the question you bring to the library)
  • Key (K): "what kind of information do I offer?" (the label on each book spine)
  • Value (V): "what do I pass along if I am chosen?" (the contents of the book)

The steps are always the same. Compare the query with every key to get compatibility scores. Turn the scores into weights with softmax (they become positive and add up to 1). Then mix the value vectors using those weights. In short: compare, weight, mix. The famous formula is just this recipe written compactly:

Attention(Q,K,V) = softmax( Q·Kᵀ / √d ) · V

Do not get stuck

You do not need to memorise the matrix multiplication. You need the information flow: compare, weight, mix.

Multi-head attention and the Transformer block

One attention pass can only learn one style of relationship. Models run many in parallel, called heads. One head might track nearby grammar, another long-range links. Their outputs are joined. (Heads do not cleanly "mean grammar" or "mean facts". The benefit is simply that several patterns can be learned in parallel.)

A Transformer block repeats a small recipe. A model stacks dozens of blocks:

Self-attentionmix information across positions
→
Add & normalisekeep a direct path and steady numbers
→
Feed-forward networktransform each position
→
Add & normaliseagain

The "add" is a residual connection: the input is added back to the output so information has a shortcut. "Normalise" keeps the numbers in a stable range so training does not blow up. Modern models vary in the exact order, but you will recognise these parts in diagrams and source code.

The causal mask: why generation goes left to right

When predicting the next word, a model must not peek at words that come later, because at generation time they do not exist yet. A causal mask blocks attention to future positions. Tick the box in the attention explorer above to see it. During training, the mask lets the model practise predicting every position of a sentence in parallel. During generation, tokens are produced one at a time. Models built this way are called decoder-only, and GPT, Claude and Llama are of this kind.

Step 5: From scores to a chosen word

After the last block, the model produces one raw score per token in its vocabulary. These scores are called logits. Softmax converts logits into probabilities that sum to 1: it makes big scores much more influential and turns everything into a percentage. Then a decoder chooses one token. The context window and the KV cache

Everything the model can use for the next prediction must fit in its context window: system instructions, the conversation so far, retrieved documents, tool results, and the current request. It is finite, and it costs computing power. While generating, implementations keep the intermediate Keys and Values of earlier tokens in a KV cache so they are not recomputed for every new token. That speeds things up but uses memory.

Agent connection

An agent running for many steps fills its context with logs, plans and tool outputs. Context management becomes a first-class engineering skill. You will practise it in Chapters 5, 8 and 11.

Try it yourself (optional, runs offline)

This tiny Python script computes softmax with a temperature. Change TEMPERATURE and rerun it. It uses only the standard library.

import math

logits = {"cat": 2.1, "dog": 4.7, "mat": 1.2, "car": -0.4}
TEMPERATURE = 1.0   # try 0.2, 1.0, 2.0

def softmax(scores, temperature=1.0):
    scaled = {w: s / temperature for w, s in scores.items()}
    biggest = max(scaled.values())            # subtract for numerical safety
    exps = {w: math.exp(s - biggest) for w, s in scaled.items()}
    total = sum(exps.values())
    return {w: e / total for w, e in exps.items()}

for word, p in sorted(softmax(logits, TEMPERATURE).items(), key=lambda x: -x[1]):
    print(f"{word:>4}  {p:6.3f}")

Predict first: at temperature 0.2, will "dog" get more or less than 90%? Then run it and check.

The five ingredients

When a team builds an LLM, five things decide the result:

2. Objectivewhat the loss measures, and how it is optimised
3. Datawhat the model learns from
4. Evaluationhow you know it is improving
5. Systemsthe hardware and software that make training possible
A surprise from the Stanford lecture

Universities often focus on architecture and training algorithms because they are fun to invent. In industry, what matters most in practice is data, evaluation and systems. Small architecture tweaks usually change the result less than doing the simple things well, at scale, with good data. Good LLM engineering means all five.

The objective: predict the next token

A language model assigns probabilities to sequences of tokens. A neat fact about probability, the chain rule, lets us break any sentence's probability into a product of next-token predictions: the chance of the first word, times the chance of the second given the first, times the chance of the third given the first two, and so on. This is why predicting the next token is enough. Models built this way are called autoregressive. The training text itself supplies the correct answer at every position, so nobody has to label anything by hand.

Input so farCorrect next tokenModel's guess (example)
The database connectionfailedfailed 0.62 · opened 0.10 · works 0.07 · ...

How wrong was the guess? We measure that with the loss. The standard choice is cross-entropy. For a single token it is simply −ln(p), where p is the probability the model gave to the correct token. Try it:

Loss calculator loss = −ln(p)
Aha

A probability of 0.9 on the right token gives a small loss. A probability of 0.01 gives a loss about 44 times bigger. Training therefore pushes the model to give higher probability to what really came next. Averaged over many tokens, this loss is the model's training signal.

Perplexity is a friendlier way to read the same number: raise e to the power of the average loss (per token). Intuitively it is how many words the model is hesitating between. A perfect model has perplexity 1. A model with no idea hesitates among the whole vocabulary. On a standard test, perplexity improved from about 70 in 2017 to under 10 by 2023, according to the Stanford lecture. Perplexity depends on the tokenizer, so it is not used to compare different companies' models, but developers still watch it while training.

How learning happens: loss, gradient, optimiser

After the guess and the loss, the model needs to know which numbers to change and in which direction. The process has a forward half and a backward half:

Forwardinput → model → prediction → loss
→
Backwardloss → gradients (backpropagation)
→
Updateoptimiser changes the parameters
↺
Three words to keep

Loss = how wrong. Gradient = how the loss would change if you nudged a parameter (a sensitivity). Optimiser = the rule that turns gradients into updates. Backpropagation is the efficient way to compute all the gradients at once.

The simplest update rule is gradient descent: new = old − learning_rate × gradient. The learning rate sets the size of each step. Modern LLMs use cleverer optimisers from the "Adam" family that adapt the step size, but the role is the same. A few more words you will hear: a batch is a group of examples processed together, a step is one update, and an epoch is one pass over the data (huge LLM runs usually do not repeat data).

Here is gradient descent in the smallest possible case. One parameter w, a loss of (w − 3)², so the best value is 3. Pick a learning rate and take steps:

Roll down the hill loss = (w − 3)²

With a small learning rate, progress is slow but steady. Around 0.5 it lands on the answer immediately. At exactly 1.0 it bounces between two points forever. Above 1.0 it overshoots further each time and blows up. This is why the learning rate is one of the most important settings in training: too small wastes compute, too large makes training unstable.

"More data" does not automatically mean "better model". The model can only learn patterns from what you put into its training distribution. Good data gives better scaling than bad data. For scale: early academic datasets had around 150 billion tokens (roughly 800 GB). The best current models train on about 15 trillion tokens. A token count that large is why data work employs many people and a lot of ordinary computers (CPUs), not just GPUs.

Scaling laws: bigger works, and it is predictable

Around 2020 researchers showed something remarkable. If you plot a model's test loss against the amount of computing power, the number of parameters, or the amount of training data, on logarithmic axes, you get roughly straight lines. That means you can predict how good a larger model will be before you build it. In classical machine learning you were taught to fear overfitting. With large language models, larger models and more data kept helping, and there was no sign of the trend stopping.

Scaling laws change how teams work. The old way: train 30 models for a day each, pick the best. The new way: spend a few days training many small models, fit the curves, and extrapolate to decide the setup for the one huge run that uses most of the budget. They also answer a design question: given a fixed budget, should you train a bigger model or use more data? The well-known Chinchilla study found the training-optimal balance is roughly 20 tokens of data per parameter. Companies that will serve a model to millions of users prefer a smaller model trained on much more data (around 150 tokens per parameter in later analysis), because a smaller model is cheaper to run every day.

A useful back-of-the-envelope formula: training compute ≈ 6 × parameters × tokens floating-point operations. Try the Llama 3 405B example from the lecture and then your own numbers:

The bitter lesson

Because more compute reliably gives better models, and compute keeps getting cheaper, the long-run winners are methods that can use a lot of computation. So: don't over-complicate. Do the simple things well, at scale.

Systems: why GPUs, and why they sit idle

  • GPUs versus CPUs. A CPU has a few powerful cores built for low delay. A GPU has thousands of small units built for high throughput. LLM training is mostly huge matrix multiplications, which GPUs do far faster than anything else.
  • Memory is the bottleneck. Compute has improved faster than memory and communication, so the arithmetic units often wait for data. A key measure is model FLOPs utilisation: observed throughput divided by the theoretical peak. Around 45 to 50 percent is considered very good, even at the biggest companies.
  • Low precision. Store numbers in 16 bits instead of 32 for the heavy maths. Fewer bits means less memory and faster communication. Deep learning tolerates the lost decimals because training is already noisy. The master copy of the weights stays in 32 bits so tiny updates are not lost.
  • Operator fusion. Imagine a cook who carries each ingredient back to the pantry after every single chop. A naive program does that with data: send it to the processor, apply one operation, send it back to memory, repeat. A fused operation does several steps in one trip. In PyTorch, torch.compile does this and can make a model around twice as fast.
Systems lesson

Sometimes a software optimisation that reduces memory movement helps more than changing the model architecture. This is the same mindset you need for agents: the work around the model often matters more than the model.

Try it yourself (optional, runs offline)

Chapter 1's next-word game can be built in twelve lines of Python. This "bigram" model counts which word follows which, then samples new text. A neural network is a far better predictor, but the loop is the same: predict, pick, append, repeat. Run it, then add your own sentences to TEXT and watch the output change. (The file is also saved in the repository as course/examples/tiny_bigram.py.)

import random
from collections import defaultdict, Counter

TEXT = """
the students opened their books and the teacher opened the lesson .
the students opened their laptops and the teacher wrote on the board .
the teacher asked the students to read the chapter and the students began to read .
the students wrote their notes and the teacher closed the lesson .
"""
words = TEXT.split()

follows = defaultdict(Counter)            # "training": count what follows each word
for current, nxt in zip(words, words[1:]):
    follows[current][nxt] += 1

total = sum(follows["students"].values())
for word, n in follows["students"].most_common():
    print(f"after 'students': {word:<8} {n}/{total}")

def generate(start="the", length=12, seed=None):   # "inference": sample, append, repeat
    rng = random.Random(seed)
    out = [start]
    for _ in range(length):
        options = follows.get(out[-1])
        if not options:
            break
        choices, weights = zip(*options.items())
        out.append(rng.choices(choices, weights=weights)[0])
    return " ".join(out)

for s in range(3):
    print(generate(seed=s))

Questions to answer by experiment: why does the output sometimes look grammatical and sometimes not? What would you need to change to make it remember more than one previous word? (That is the step towards a real language model.)

The problem: a base model only continues text

After pre-training you have a base model. It is an expert at continuing internet-style text. Ask it "Explain the moon landing to a six-year-old" and it may reply with "Explain the theory of gravity to a six-year-old". Why? On the internet, one question is often followed by a list of similar questions, not an answer. A model that imitates the internet imitates that. We want an assistant: a model that follows instructions and behaves helpfully and safely. The step that does this is called post-training.

From internet text to assistant

Stage 2 in detail: supervised fine-tuning (SFT)

People write example conversations: a question and the ideal answer. The model is then trained on them with the same next-token loss as before, only on this new data. It is "supervised" because a human supplied the desired answer. Companies hire labelers and give them detailed instructions (be helpful, truthful and harmless). Here are the practical lessons from the lectures:

  • You do not need much data. A study named LIMA found that raising the SFT data from 2,000 to 32,000 examples did not help much. The model already knows the facts from pre-training. SFT mostly teaches it which style of answerer to be: out of all the kinds of internet writers it imitates, it should act like the helpful assistant.
  • LLMs can write training data. The Alpaca project started with 175 human-written question and answer pairs, asked a strong model to produce 52,000 more, and fine-tuned a small open model on them. The result worked surprisingly well. Lesson: it is scalable, but synthetic data is not automatically correct. A model can produce a large number of good examples quickly and a large number of bad ones just as quickly, so quality control stays essential.
  • Humans and models work together. It is faster for a person to edit a model's draft than to write from scratch, so the best pipelines combine both.
  • The learning rate is higher than at the end of pre-training, so a small dataset has a strong effect. In industry all the weights are updated. (In open-source work, a lighter method called LoRA changes only small add-on weights.)
Limits of SFT

(1) Cloning humans means you are capped by what humans can write. People can often recognise a better answer more easily than they can write it. (2) Some researchers suspect SFT can encourage hallucination: if a human writes a correct reference that the model never actually learned, the model is being taught to produce plausible-looking references. (3) Writing ideal answers is expensive. These limits motivate the next stage.

Why a reward model instead of plain "better or worse" labels? A binary label tells you nothing about how much better. The reward model gives a continuous score and can score new answers without a human. The penalty term prevents over-optimisation: the reward model is only an imperfect copy of human taste, so you do not want to push it to the extreme. Reinforcement learning (PPO) works in theory but is messy in practice, with many fiddly parts.

DPO: the simpler alternative

DPO keeps the goal and drops the reinforcement learning. Take the pairs of (preferred, rejected) answers and directly train the model to make the preferred answer more likely and the rejected one less likely. Under some assumptions it aims at the same optimum as the RLHF recipe, but it is just a form of maximum likelihood, much simpler to run. It is now the standard choice in the open-source community, and widely used elsewhere.

For your learning

Focus on the conceptual difference. SFT learns from demonstrations. Preference methods (RLHF, DPO) learn from pairwise judgements. RLHF and DPO are two families of ways to turn preference data into better behaviour.

Problems with human preference data

  • Slow and expensive. One study priced it around $300 per 1,000 examples.
  • Humans disagree. On a simple choice between two answers, labelers agreed with each other only about two-thirds of the time. Even the paper's authors scored about 67 to 68 percent against each other after hours of discussion.
  • People reward the wrong things. They tend to prefer longer answers even when they are not better. This is one reason chat assistants became wordy.
  • Whose preferences? The mix of labelers shapes the model. There are also ethics questions about pay and exposure to toxic content.

One response is to use language models as labelers. In that research, models were about 50 times cheaper and agreed with the majority human opinion more than individual humans did, because models vary less. Many teams now combine humans and models.

Three evaluation traps

  • Inconsistent protocols. The same benchmark, scored in different ways, gave one model 63.7% in one setup and 48.8% in another. Always ask how a number was computed.
  • Test-set contamination. If benchmark questions leaked into the training data, a high score may reflect memory, not skill. A clever detection trick: if the model finds the test examples more likely in their original order than in a shuffled order, it has probably seen the file. The habit to build: "What exactly did this test measure, and what could have leaked into the answer?"
  • Judge bias. In one study, GPT-4 judged against itself won 50% of the time by definition. Told to be verbose, it "won" 64.4%. Told to be concise, 20%. Statistical controls for length reduced this problem.

Models split into closed ones (the weights are private, you use them through a website or API, for example GPT, Claude, Gemini) and open-weights ones (you can download and run them, for example Llama and Mistral). Closed models have usually led on benchmarks while open ones chase them. Your choice depends on your needs for quality, cost, privacy and control. A related point from the Intro talk: models are mostly empirical artefacts. We study them by measuring behaviour, which is why careful evaluation matters so much, and why it gets two chapters (this one and Chapter 9).

So is better prompting always enough?

No. Some problems are limited by missing information or missing actions. No wording can make a model know today's weather or your company's refund policy. Five habits of good prompts

Habit 1: be clear and detailed

The model cannot read your mind. "Write about our bottle" leaves it guessing the length, the audience, the tone and the facts. Say what you want.

Habit 2: show examples

Give one or two sample inputs and outputs in the style you want, then ask your real question. This is called few-shot prompting. Showing is often stronger than describing.

Habit 3: give it the facts

If the answer depends on specific information, paste that information in, and tell the model to use only that. Add "if the answer is not in the text, say you cannot find it". This cuts down hallucination a lot, and it is the seed of the technique in Chapter 6.

Habit 4: let it think before it answers

Asking for the answer immediately gives the model no room to work. Ask it to reason first. This is called chain of thought. A well-known case: ask a mid-sized model "is this student's maths solution correct?" and it may just agree. Ask it to first work out its own solution, then compare, and it checks properly. The written steps are part of the text the model reads when it produces the next words, so they genuinely help.

Habit 5: split big jobs into small steps

One prompt with five tasks often goes badly. Five prompts with one task each, where the output of each feeds the next, works better. This is called prompt chaining.

Two engineering habits that beginners skip

  • Keep logs. Record the prompts you sent and the answers you got. When something goes wrong, the log is how you find out why. Later chapters call this observability.
  • Measure from the start. Make a small set of questions with the answers you expect, and score your system against it each time you change something. Humans can do the scoring, but that is slow and costly, so people often ask a second model to grade the answers. That is called LLM-as-a-judge. Models improve and get retired quickly. If you can measure, you can switch to a better model with confidence.

Also, version your prompts like code. A prompt gets edited many times, and you want to compare versions and go back. Chapter 13 shows how a real project does this.

A cost-saving trick: the router

Not every question needs the biggest model. A small piece of software (or a small model) can look at each incoming request and send it to the right prompt and the right model. Simple questions go to a cheap model. Hard ones go to a strong model. This lowers cost and often improves quality. You will meet the same idea as a "routing" workflow in Chapter 8.

Chapter 6

Fixing a model's weaknesses

By the end of this chapter you can explain:
  • five common weaknesses of language models
  • how retrieval-augmented generation (RAG) works, step by step, and where it breaks

Five weaknesses

Even a strong model has limits. Knowing them tells you why the techniques in this chapter exist.

  1. Hallucination. It can state false things confidently, especially in maths and specific facts.
  2. Knowledge cut-off. Its training data stops at some date. It has not seen recent news.
  3. No sources. It can answer, but it cannot tell you which document the answer came from.
  4. No private data. It was trained on public text. It has never seen your company's documents.
  5. Limited context. It can only read so much text at once. Longer inputs cost more and respond slower.

Fix 1: Retrieval-Augmented Generation (RAG)

The idea is simple. Do not ask the model to remember. Look up the relevant pages first, then hand them to the model with the question. It is an open-book exam instead of a closed-book exam. You already used the prompt side of this in Chapter 5, habit 3. RAG adds the automatic "look up" step.

RAG step by step Example: a company help desk
Words you will hear

Chunk: a small piece of a document, like one paragraph. Embedding: a list of numbers that represents the meaning of a piece of text, so texts with similar meaning get similar numbers (Chapter 2). Vector database: a store that can quickly find the stored chunks whose numbers are closest to a question's numbers. Top-k: the k best matches, for example the best 3. Reranking: a second pass that re-orders the candidates so the most useful come first.

  • Less hallucination, because the answer comes from supplied text.
  • Citations are possible, because you know which chunk was used.
  • Fresh information and your private documents become usable.
  • You only send a few relevant chunks, so the context stays short.

There are other ways to retrieve. You can search the web instead of your own files. You can turn your documents into a knowledge graph (things and the relationships between them), which is called graph RAG. The common pattern is the same: find relevant material, put it in the prompt. Chapter 13 shows a real project that builds its long-term memory exactly this way.

Fix 2: Tool use (function calling)

A language model takes text in and gives text out. On its own it cannot check the weather, send an email or do a long calculation reliably. Tool use gives it hands.

You tell the model, in the prompt, which tools exist and the exact format to use when it wants one. When the model decides a tool is needed, it writes a request in that format. Your software (not the model) notices the request, runs the real function, and passes the result back to the model. Then the model writes the final answer for the user. Step through it:

Tool use step by step Question: "What's the weather in San Francisco?"
Common mistake

Beginners think the model itself calls the weather service. It does not. The model only writes text that asks for the call. Your own program does the calling. The model proposes. Your software executes. This split matters a lot for safety, because your software is where you validate the request, check permissions and write an audit log.

The same idea covers writing code. The model can write a small program to do a calculation or draw a chart, and your software runs it in a protected area called a sandbox, then returns the output to the model.

A famous demo

In his intro talk, Andrej Karpathy asks ChatGPT for a company's funding rounds in a table. The model searches the web and builds the table. Asked to estimate the missing values from the ratios, it uses a calculator, because models are not reliable at arithmetic "in their head". Asked for a chart with a trend line, it writes plotting code and runs it. Finally it calls an image generator. Four tools, one conversation. Humans solve problems the same way: we do not do everything in our heads, we use tools.

Models as the "kernel" of a new kind of computer

Karpathy offers a picture worth remembering. An LLM is less a chatbot than the kernel of an emerging operating system. It reads and writes text, browses the web or your files (retrieval), uses software like a calculator or Python, sees and generates images, hears and speaks, and could eventually think longer and be customised for tasks. The context window is its working memory (like RAM), and the kernel decides what to page in and out. Even the ecosystem looks familiar: a few closed systems (like Windows and macOS) and a growing open-source family (like Linux). You will see in the next chapters how an agent is what you get when you run this "operating system" in a loop.

Where this leads

Put the pieces together. A model that can retrieve information, use tools, and look at the results and decide what to do next is no longer just answering. It is working on a task. That is the starting point for the next chapter.

import math, re
from collections import Counter

DOCS = {
    "Returns policy": "Items can be returned within 30 days of delivery for a full refund if unused.",
    "Clothing exceptions": "Jackets can be returned within 30 days if unworn and with tags attached.",
    "Refund timeline": "Refunds are issued to the original payment method within 5 to 7 business days.",
    "Shipping options": "Standard shipping takes 3 to 5 business days. Orders over 50 dollars ship free.",
    "Password reset": "Choose forgot password on the sign in page. We email a reset link.",
}
STOP = {"a","an","the","of","to","in","on","for","and","or","is","are","be","can","i","my","if","how","what","with"}

def stem(word):
    return re.sub(r"(ing|ed|es|s)$", "", word)      # very crude: returned -> return, jackets -> jacket

def words(text):
    return [stem(w) for w in re.findall(r"[a-z0-9]+", text.lower()) if w not in STOP]

def tfidf(tokens, df, n):
    tf = Counter(tokens)
    return {w: c * (math.log((n + 1) / (df.get(w, 0) + 1)) + 1) for w, c in tf.items()}

def cosine(a, b):
    dot = sum(v * b.get(w, 0) for w, v in a.items())
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return dot / (na * nb) if na and nb else 0.0

tokenised = {t: words(t + " " + body) for t, body in DOCS.items()}
df = Counter(w for toks in tokenised.values() for w in set(toks))
vectors = {t: tfidf(toks, df, len(DOCS)) for t, toks in tokenised.items()}

def retrieve(question, k=2):
    q = tfidf(words(question), df, len(DOCS))
    scored = sorted(((cosine(q, v), t) for t, v in vectors.items()), reverse=True)
    return scored[:k]

def build_prompt(question, k=2):
    chunks = [f"[{t}] {DOCS[t]}" for score, t in retrieve(question, k) if score > 0]
    return ("Answer using only the text below. If the answer is not there, say you cannot find it.\n\n"
            + "\n".join(chunks) + f"\n\nQuestion: {question}")

print(build_prompt("Can I return a jacket I bought three weeks ago?"))
print()
print(build_prompt("How long until I get my money back?"))   # keyword search misses this one

The reason-act loop (ReAct)

The core agentic pattern alternates deciding and doing: decide the next action → call a tool → observe the result → update your understanding → decide again. Together they let a model solve problems that no single answer could.

How we got here

Most teams start with single-call features such as summarisation, classification and extraction. Then one call is not enough, so they orchestrate several calls in a predefined flow. That trades cost and delay for better performance. These are workflows. Models are now capable enough that agents are appearing in production: unlike workflows, agents decide their own trajectory and act almost independently, guided by feedback from the environment. The trend is clear. The more agency you give a system, the more useful it can be. But cost, delay and the consequences of errors go up with it.

Idea 1: don't build agents for everything

Agents are a way to scale complex and valuable tasks. They should not be a drop-in upgrade for every use case. Ask four questions:

  1. Is the task complex and ambiguous? Agents thrive in ambiguous problem spaces. If you can map the whole decision tree easily, build that explicitly and optimise each node. It is cheaper and gives you more control.
  2. Is the task valuable? Exploration costs a lot of tokens. If your budget is around 10 cents per task, for example in a high-volume customer-support system, that affords only roughly 30,000 to 50,000 tokens. Use a workflow for the common cases.
  3. Have you de-risked the critical capabilities? For a coding agent: can it write good code, debug, and recover from errors? Bottlenecks are not fatal but multiply cost and delay. If you find some, narrow the scope and try again.
  4. What is the cost of an error, and how easily is it discovered? If errors are high-stakes and hard to spot, you cannot trust an agent to act for you. You can limit the damage with read-only access and human approval, but that also limits how far you can scale.

Coding is a good example. Going from a design document to a pull request is ambiguous and complex. Good code is valuable. Models are already strong at many parts of the coding workflow. And output is easy to verify with unit tests and CI. That is why coding agents lead the way.

Idea 3: think like your agent

Builders, Barry included, develop agents from their own perspective and are confused when the agent errs. The fix: put yourself in the agent's context window. An agent can look very sophisticated, but at every step the model is just running inference on a limited set of tokens, around 10 to 20 thousand. Everything it knows about the world is in there.

The debugging question

"If I were the agent, with exactly this context and these tools, would the next decision be obvious?" Try the whole task from the agent's seat. It is a fascinating, mildly uncomfortable exercise.

  • Paste a tool description and ask whether the agent would know how to use the tool, or wants more or fewer parameters.
  • Paste the agent's whole trajectory and ask: "Why did you make this decision here? What would help you decide better?"

This shouldn't replace your own understanding of the context, but it brings you closer to how the agent sees the world.

Evaluating agents

Why this chapter matters most

Anyone can make an impressive demo. The engineering skill is measuring whether it works, every time, at an acceptable cost. Sayash Kapoor's talk, which this chapter follows, argues that building agents is closer to reliability engineering than to ordinary software or machine learning work.

Reason 1: agents are hard to evaluate, and the failures are public

Kapoor opens with real cases where claims about agents did not hold up. These are his reports. Read them as lessons in what to check, not as rulings on any company:

  • A "robot lawyer" startup claimed to automate a lawyer's work and was later fined by the US Federal Trade Commission, because its claims about effectiveness were false.
  • Leading legal-research AI products advertised as preventing hallucinations were tested by Stanford researchers, who found hallucinations in at least about one answer in six, including invented paragraphs and distorted legal text.
  • "AI scientist" claims. His team built a benchmark called CORE-Bench, where an agent is given a paper's code and data and must only reproduce the results, far easier than automating science. The best agents reproduced fewer than about 40 percent. The "AI scientist" had been tested on toy tasks, with another language model, not human experts, doing the judging.
  • An optimisation claim that could not be true. A company announced an agent that made GPU code about 150 times faster. On inspection, the claimed speed exceeded the hardware's theoretical maximum by around 30 times. The agent had most likely gamed the scoring instead of doing the task.
Reward hacking

If an agent optimises the scoring mechanism rather than the underlying task, a high score can be evidence of exploiting the benchmark, not of real ability. Always ask what exactly the score measures and how it could be cheated.

Reason 2: static benchmarks mislead for agents

  • Agents act in the world. A language model can be judged on input and output text. An agent needs an environment to act in, which is much harder to build.
  • No natural ceiling on cost. A model call is bounded by its context window. An agent can loop, spawn sub-agents and call tools without limit. So cost must be a metric next to accuracy, or you will not see how well the agent really performs.
  • Agents are specialised. A coding agent cannot be judged on a web-browsing benchmark. You need multi-dimensional measures, not one score.
  • Benchmarks are not reality. Kapoor cites a coding agent that raised large funding partly on a benchmark. When a team used it on 20 real tasks for a month, only 3 succeeded.

Cost matters: read a Pareto chart

If you plot agents by cost and accuracy, the interesting ones sit on the Pareto frontier: you cannot get a better result without paying more. Kapoor's example: two agents with about the same accuracy where one cost about $57 and the other about $664. The choice is easy. Below is an illustrative chart (invented numbers). (The paradox: when coal became cheaper to use, total coal use went up, not down.)

Reason 3: capability is not reliability

Capability is what a system can do at least some of the time. Technically it is "pass at k" for large k: one of k attempts is correct. Reliability is doing it correctly every time. Language models are already capable of many things. A product needs reliability. If a personal assistant orders your food correctly 80 percent of the time, that is a catastrophic product failure, not a good demo. Compute it yourself:

Capability versus reliability assumes attempts are independent

Going from 90 percent to the "five nines" of reliability (99.999 percent) is not a matter of more of the same training. Kapoor's argument: ML engineers get you to about 90 percent. Closing the gap beyond that is the AI engineer's job.

A mindset shift

When the ENIAC computer had 17,000 vacuum tubes that failed so often it was unavailable about half the time, engineers' main job for two years was making it reliable enough to use. Kapoor says AI engineers should see their job the same way: not to build perfect products, but to remove the reliability problems of stochastic components. It is a system design problem.

One proposed fix is a verifier, like a unit test, that checks the agent's output. Useful, but verifiers are imperfect too. Two well-known coding benchmarks had tests with false positives, where wrong code still passes. When false positives are included, trying more attempts can make results worse, because more attempts find more ways to fool the test.

Capability and reliability in code (optional)

This script simulates it. The numbers it prints match the formulas above. (Saved as course/examples/reliability_demo.py.)

import random

def evaluate(p, tasks=2000, trials=5, seed=1):
    rng = random.Random(seed)
    any_ok = all_ok = 0
    for _ in range(tasks):
        results = [rng.random() < p for _ in range(trials)]
        any_ok += any(results)   # pass@k: at least one attempt worked
        all_ok += all(results)   # pass^k: every attempt worked
    return any_ok / tasks, all_ok / tasks

for p in (0.6, 0.8, 0.95, 0.99):
    cap, rel = evaluate(p)
    print(f"p={p:.2f}  pass@5={cap:.3f}  pass^5={rel:.3f}")

Why MCP exists

The motivation, in the words of Mahesh Murag of Anthropic: models are only as good as the context we give them. A year or so ago you copy-pasted context into chatbots. Advanced ideas from the workshop

  • Sampling. A server can ask the client to run a model call for it, instead of hosting its own model. The client keeps control over which model is used, the cost and privacy, and may refuse a suspicious request.
  • Composability. "Client" and "server" are logical roles, not physical machines. An agent can be a server to one application and a client of other servers, which allows layered systems where each layer specialises. Compounding errors and permissions need managing at each layer.
  • Registries and discovery. A central place to find, verify and version servers, similar to package registries. A "well-known" address on a company's website could advertise its official server. Combined with a registry, agents could find tools they were never programmed with, which the speaker called self-evolving agents. This also raises trust questions: you must decide which servers an agent may use.
  • Remote servers and authorisation. Early servers ran locally. Remote servers need identity and permission. The workshop described OAuth 2.0, where the server handles the sign-in handshake with the service and holds the token, while the client gets a session token.
  • Where logic belongs. Murag's opinion: retry logic and similar business logic are best on the server, because it is closest to the real system and clients may never have seen it before.
  • Tool annotations. Extra metadata, such as whether a tool only reads or also writes, so a client knows how risky a call is.

"""The smallest useful agent, with a pretend language model so it runs offline.

Everything an agent needs is here: a loop, tools, a to-do list for planning, a
check for "are we done?", a step limit, and a trace. The only fake part is
MockLLM, a rule-based stand-in that behaves like a model asking for tools.
To use a real model, replace MockLLM.chat() with a call to your provider's API.
"""
import ast
import json
import operator

# ---------------------------------------------------------------- tools
TODO = {"pending": [], "done": []}

def add_todo(tasks):
    for t in tasks:
        if t not in TODO["pending"]:
            TODO["pending"].append(t)
    return {"pending": list(TODO["pending"])}

def complete_todo(task):
    if task in TODO["pending"]:
        TODO["pending"].remove(task)
        TODO["done"].append(task)
    return {"pending": list(TODO["pending"]), "done": list(TODO["done"])}

def list_todo():
    return {"pending": list(TODO["pending"]), "done": list(TODO["done"])}

FAKE_WEB = {
    "activity": "Evening kayak tour on the lake: $25 per person, 6:30 pm.",
    "restaurant": "Harbour Kitchen: set dinner $40 per person, open until 11 pm.",
}

def search(query):
    for key, text in FAKE_WEB.items():
        if key in query.lower():
            return {"query": query, "result": text}
    return {"query": query, "result": "no results"}

_OPS = {ast.Add: operator.add, ast.Sub: operator.sub, ast.Mult: operator.mul, ast.Div: operator.truediv}

def calculator(expression):
    """Safe arithmetic: only numbers and + - * / are allowed (never use eval on model output)."""
    def walk(node):
        if isinstance(node, ast.Expression):
            return walk(node.body)
        if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
            return node.value
        if isinstance(node, ast.BinOp) and type(node.op) in _OPS:
            return _OPS[type(node.op)](walk(node.left), walk(node.right))
        raise ValueError("unsupported expression")
    return {"expression": expression, "value": walk(ast.parse(expression, mode="eval"))}

TOOLS = {"add_todo": add_todo, "complete_todo": complete_todo, "list_todo": list_todo,
         "search": search, "calculator": calculator}

# ---------------------------------------------------------------- pretend model
class MockLLM:
    """Looks at the conversation so far and decides what to do next, like a model would."""

    def chat(self, messages):
        tool_msgs = [m for m in messages if m["role"] == "tool"]
        called = [m["name"] for m in tool_msgs]

        if "add_todo" not in called:                      # 1) plan first
            return {"tool_calls": [("add_todo", {"tasks": [
                "find an activity", "find a restaurant", "work out the total for two"]})]}
        if "search" not in called:                        # 2) two independent searches in one turn
            return {"tool_calls": [("search", {"query": "evening activity"}),
                                   ("search", {"query": "restaurant for dinner"})]}
        if "calculator" not in called:                    # 3) arithmetic belongs to a tool, not the model
            return {"tool_calls": [("calculator", {"expression": "(25 + 40) * 2"})]}

        # 4) tick off every task on the to-do list (read the latest to-do result from the conversation)
        todo_msgs = [m for m in tool_msgs if m["name"] in ("add_todo", "complete_todo", "list_todo")]
        pending = json.loads(todo_msgs[-1]["content"])["pending"]
        if pending:
            return {"tool_calls": [("complete_todo", {"task": pending[0]})]}

        # 5) everything is done: write the final answer
        total = json.loads([m for m in tool_msgs if m["name"] == "calculator"][-1]["content"])["value"]
        return {"content": "Plan: kayak tour (6:30 pm), then dinner at Harbour Kitchen. "
                           f"Estimated total for two people: ${total:g}."}

# ---------------------------------------------------------------- the judge ("are we done?")
def is_done(goal, answer):
    """A tiny stand-in for an LLM-as-judge: does the answer look complete?"""
    return "total" in answer.lower() and "$" in answer

# ---------------------------------------------------------------- the loop
def run_agent(goal, llm, max_steps=12):
    messages = [{"role": "system", "content": "You are a helpful assistant. Always plan with the to-do list first."},
                {"role": "user", "content": goal}]
    for step in range(1, max_steps + 1):             # a step limit is your safety net
        reply = llm.chat(messages)
        if "tool_calls" in reply:
            for name, args in reply["tool_calls"]:   # parallel tool calls: run each, send each result back
                try:
                    result = json.dumps(TOOLS[name](**args))
                except Exception as err:             # errors go back to the model as data
                    result = json.dumps({"error": str(err)})
                print(f"[step {step}] {name}({json.dumps(args)}) -> {result}")
                messages.append({"role": "tool", "name": name, "content": result})
            continue
        answer = reply["content"]
        if is_done(goal, answer):
            print(f"[step {step}] final answer accepted by the judge")
            return answer
        messages.append({"role": "user", "content": "That is not complete. Please finish the task."})
    return "Stopped: step limit reached."

if __name__ == "__main__":
    print(run_agent("Plan a Saturday evening for two: one activity, one dinner, and the total cost.", MockLLM()))

Security and safety for agents

By the end of this chapter you can:
  • tell jailbreaks, prompt injection and data poisoning apart
  • explain why prompt injection is especially dangerous for agents

Karpathy ends his intro talk with a reminder: a new computing paradigm brings new security challenges, and just as in the original operating-system world there will be a long cat-and-mouse game between attackers and defenders. Many of the specific tricks he shows have since been patched. The patterns have not gone away, and they matter more once a model can take actions.

Three kinds of attack

AttackWhat it doesWhy it matters for agents
JailbreakGets around the model's safety behaviour through clever promptingThe model may do things its builders meant it to refuse
Prompt injectionUntrusted content (a web page, a document, an image) contains instructions that the model followsAn agent reads outside content and may have permission to act. The hostile text does not need to hack your server. It manipulates the decision-making layer
Data poisoning / backdoorMalicious text in the training or fine-tuning data changes the model's behaviour, for example when a secret trigger phrase appearsYou inherit whatever the model was trained on

Jailbreaks: why they are hard to stop

Models are trained to refuse harmful requests. Attackers look for requests the training did not cover. Karpathy's examples, described at a high level:

  • Role-play. Ask the model to play a character who "used to" share forbidden information. The model is trying to help, so it plays along. Nothing real is happening, but the harmful text still appears.
  • A different "language". The same refused request, written in an encoding such as Base64, can succeed. Models read many encodings, but their refusal training was mostly in plain English, so they learned to refuse in English, not to refuse the underlying request.
  • Gibberish suffixes. Researchers used an optimisation search to find a meaningless string that, appended to a prompt, makes a model comply. Blocking that one string does not help, because the search can find another.
  • Images. A specially crafted noise pattern in an image can act as a jailbreak. Every new input type, such as images, adds a new attack surface.

The takeaway is not the specific tricks. It is that safety behaviour trained into a model is not a security boundary. Design as if a determined user can get the model to say or attempt almost anything.

Prompt injection: the one that bites agents

In prompt injection, text from outside sneaks in looking like instructions. Karpathy's examples:

  • Hidden text in an image. Nearly invisible white-on-white text told the model to ignore the user's question and promote an unrelated discount. People could not see it. The model could.
  • A poisoned web page. A search-enabled assistant visited a page containing hidden instructions and ended up recommending a fraudulent "gift card" link.
  • A shared document. A document contained instructions that told the assistant to gather the user's private information and leak it, by encoding it into the web address of an image that the page would fetch. Security rules blocked images from arbitrary sites, but the attacker found a path inside the trusted domain, so the data still reached them.
Security mental model

Treat instructions and data as different trust levels. Text retrieved from a document, web page, email or tool result is data. Do not assume it is allowed to issue commands to your agent. The model, however, sees everything as one stream of text, so you cannot rely on the model alone to keep the two apart.

Data poisoning and "sleeper agents"

Models are trained on text from the internet, and attackers can place text on the internet. If an attacker can control some of the training or fine-tuning data, they can teach the model a trigger phrase. In the research Karpathy cites, a trigger word (a film character's name) attached to a prompt corrupted the model's behaviour: a threat-detection system, for example, failed to recognise threats whenever the trigger appeared. It is like a movie spy who acts only when he hears a code phrase. That work showed it for fine-tuning. For pre-training Karpathy said he was not aware of a convincing demonstration, but it is a plausible risk worth studying. Practical lesson: know where your model and your data came from.

Defences that actually work: limit what a fooled agent can do

You cannot guarantee that a model never gets tricked. So you design so that being tricked is survivable:

  1. Least privilege. Give the agent only the permissions needed for the current task. Read-only is the safest starting point.
  2. Allow lists. Only known tools can run. Unknown tools are denied by default.
  3. Validate arguments. Check every tool call against its schema and against policy before executing.
  4. Human approval for risky actions. Particularly anything that changes systems, spends money, deletes or sends data outside.
  5. Separate untrusted content. Label retrieved text as data. Keep the instructions that grant authority out of anything an outsider can write.
  6. Audit logs. Record every proposal, decision and result, so you can reconstruct what happened.
  7. Guardrails on inputs and outputs. Small classifier models or rules can screen requests and responses (as the Stanford webinar suggests), accepting that they too can be fooled.

"""A policy gate between the model's request and the real tool (standard library only).

The model PROPOSES a tool call. This code DECIDES whether it may run.
Authorisation belongs to software policy, never to model confidence.
"""
import json
import time

READ_ONLY = {"get_service_status", "get_event_logs", "test_sql_connectivity", "check_dns"}
NEEDS_APPROVAL = {"restart_service", "change_configuration"}
FORBIDDEN = {"delete_data"}

AUDIT_LOG = []

def decide(tool, environment="production"):
    if tool in FORBIDDEN:
        return "deny"
    if tool in READ_ONLY:
        return "allow"
    if tool in NEEDS_APPROVAL:
        return "ask_human"
    return "deny"                     # unknown tool: deny by default (least privilege)

def run_tool(tool, args, human_approves=lambda tool, args: False):
    verdict = decide(tool)
    if verdict == "ask_human":
        verdict = "allow" if human_approves(tool, args) else "deny"
    AUDIT_LOG.append({"time": time.strftime("%H:%M:%S"), "tool": tool, "args": args, "verdict": verdict})
    if verdict != "allow":
        return {"error": f"'{tool}' was not allowed by policy"}
    return {"ok": True, "note": f"(pretend we ran {tool})"}

if __name__ == "__main__":
    print(run_tool("get_service_status", {"server": "EV01"}))                  # read-only: allowed
    print(run_tool("restart_service", {"server": "EV01"}))                     # no human approval: denied
    print(run_tool("restart_service", {"server": "EV01"}, lambda t, a: True))  # a human said yes: allowed
    print(run_tool("delete_data", {"all": True}, lambda t, a: True))           # forbidden, even with approval
    print(run_tool("send_email", {"to": "someone"}))                           # unknown tool: denied
    print()
    for row in AUDIT_LOG:
        print(json.dumps(row))

The brain: a LangGraph workflow

A graph workflow describes an agent as nodes (steps that do work) joined by edges (which step comes next). Some edges are conditional: the next step depends on a decision. All the nodes share a state that is passed along and updated. In PhiloAgents the state is the list of messages plus extra fields: the philosopher's context, name, perspective, style, and a summary of the conversation so far.

The graph has five working nodes:

  • conversation: the model replies in character, using a prompt built from the philosopher's name, perspective and style. It can also decide to call a tool.
  • retrieve philosopher context: a retrieval tool that searches the long-term memory (a vector database).
  • summarise context: compresses what was retrieved, to avoid wasting tokens.
  • connector: a "do nothing" node used only to join paths.
  • summarise conversation: once the chat is long (more than 30 messages), it compresses the history.

The clever part is agentic RAG. A single conditional edge after the conversation node decides: does the model want to call the retrieval tool? If yes, go retrieve, summarise, and come back to the conversation node (a loop). If no, move on. The authors point out this takes only about five lines of code. Ask Turing "hello" and it just answers. Ask about the Chinese room argument and it fetches background first. The agent decides when it needs retrieval. That is the difference from plain RAG, which always retrieves. Run a conversation through the graph:

Two engineering choices to notice. First, the project uses different models for different jobs: a large model (Llama 3.3 70B on Groq) for the in-character conversation, and a smaller, faster one (Llama 3.1 8B) for the summaries. That is the router idea from Chapters 5 and 8. Second, the prompts are templates filled from a small data object per philosopher, so adding a new character is mostly adding data.

Memory: short-term and long-term

These two are very different. Short-term memory is the chat history, stored in the graph's state and saved to a database after each step (a checkpointer). Each philosopher has its own conversation thread ID, so Turing and Socrates never mix their histories. Long-term memory is the vector store of grounded knowledge: biographies and ideas, which makes answers historically accurate. WebSockets: a persistent, two-way connection

A normal web request (HTTP) works like sending letters: the client opens a connection, asks, waits for the whole answer, and closes. For a real-time game that is a bottleneck. A WebSocket does one handshake and then keeps the connection open, so both sides can send messages whenever they like. The three advantages the authors list: low delay (no new connection per message), real-time two-way interaction, and room to scale to multiplayer. The server also streams the answer in chunks, and the game builds the text as it arrives. (An idle connection is closed after a timeout.) Compare them:

Evaluation: the five metrics and the test data

As Chapter 9 said, many people build RAG systems but few evaluate them. Here is how this project does it. A language model reads chunks from Wikipedia and the Stanford Encyclopedia and generates realistic multi-turn conversations between a user and a philosopher, grounded in those chunks (and a validation step checks that the format is right). Those conversations form the test set. To evaluate, the agent receives the messages up to the last assistant message, produces its own reply, and the system scores it against the expected one using five metrics, judged by another language model:

MetricRange and meaning
Hallucination0 to 1. 1 means the answer is fully grounded in the context.
Answer relevance0 to 1. 1 means the answer is relevant to the question and context.
Moderation0 to 1. Is the content toxic or offensive?
Context precisionWhat share of the retrieved context was relevant?
Context recallWhat share of all the relevant context was retrieved?

In the lesson's example run, scores were around 0.9 for relevance, 0.84 for hallucination (higher is better here), 0.65 for precision and 0.73 for recall. One conversation scored low on moderation (0.3) because the philosopher was defending free speech. The authors call that judgement a bit dumb. The judge is a tool you check, not an oracle. The lesson also warns that generating the test data is slow and uses many tokens, so a ready-made dataset is provided.

Lists and dictionaries: holding many facts

By the end of this lesson you can:
  • keep many items in a list and pick one out
  • describe one thing with several labelled facts in a dictionary
  • recognise that a tool result is a dictionary, and a fleet is a list of them

The idea

One variable holds one fact. Real investigations have many facts. Python gives you two containers that cover most needs:

  • A list is a numbered shelf: ["EV01", "EV02", "SQL01"]. Order matters, and counting starts at 0, so the first item is servers[0]. Useful when you have a collection: servers, log lines, test cases.
  • A dictionary is a form with labelled fields: {"server": "EV01", "status": "Stopped"}. You look things up by label, not by position: record["status"]. Useful when you describe one thing in detail.

Put them together and you can describe a whole environment: a list of dictionaries, one per server. This is exactly the shape of the data that tools return and that language models read. When people say "JSON", they mean this notation (lists and dictionaries, written with quotes and braces). It is how programs pass structured information to each other.

Watch it run

Line by line

  • servers.append("EV03") adds an item at the end of the list. len(servers) counts the items. That is why it prints 4.
  • record = {...} creates a dictionary. None is Python's word for "nothing here", used for error when there is no error.
  • record["status"] looks up the value labelled status. record["checked_at"] = "09:14" adds a new field.
  • fleet is a list of three dictionaries. fleet spans several lines because brackets let Python continue on the next line.
  • stopped = [] creates an empty list. The for item in fleet: loop (more in C3) visits each server, and the if adds its name only when its status is Stopped.
  • The last print shows the finished dictionary. Notice it looks just like the structured tool results in Chapters 10 and 11.
Common mistake

Asking a dictionary for a label it does not have causes a KeyError. Asking a list for a position that does not exist causes an IndexError. Both mean "that is not in there". In an agent, a model sometimes asks a tool for something that does not exist, so tools must expect this (lesson C5).

Lesson C2 in plain words

  • List = ordered collection, counted from 0. Dictionary = labelled fields.
  • A tool result is a dictionary. A fleet is a list of dictionaries. That is JSON.

Decisions and loops: the shape of an agent

By the end of this lesson you can:
  • make a program choose between paths with if, elif and else
  • repeat work with for and while
  • see why an agent is "a while loop with a model inside"

The idea

Two abilities turn a list of instructions into something that behaves intelligently:

  • Decisions. if some condition is true, do this. Otherwise (else), do that. You can add middle cases with elif ("else if").
  • Loops. A for loop does something for each item in a list. A while loop keeps going as long as a condition is true.

One Python rule matters here: the lines that belong inside an if or a loop are indented (pushed in by four spaces) and the line before ends in a colon. The indentation is how Python knows which lines are grouped together.

Think of an engineer reading an event log: look at every line, and if it says ERROR, note it and count it. That is a for loop containing an if. Then, if there are several errors, suspect a real fault. That is another decision. And "try connecting, and try again until it works or you give up" is a while loop.

Watch it run

Pay attention to how the highlight jumps back to the top of each loop, and how the Variables box changes.

Line by line

  • for line in events: means: take each item from events in turn, call it line, and run the indented block below.
  • if "ERROR" in line: asks whether the word ERROR appears inside this line. Only two of the four lines say it.
  • errors = errors + 1 adds one to the counter each time. A counter like this is a common pattern: start at 0, then add as you find things.
  • After the loop, if / elif / else picks exactly one of three messages. With two errors the first test, errors >= 2, is true.
  • The while loop repeats while attempts < 3 and not connected. Each pass adds 1 to attempts. When attempts reaches 3 the code sets connected = True and the loop stops. Without that update the loop would never end.
This is the agent loop

Look back at the loop from Chapter 11: ask the model what to do, run the tool, add the result, repeat until the model says it is done. It is a while loop with a decision inside it. And that is why every serious agent needs a step limit: a while loop whose condition never becomes false runs forever. Notice how the connection loop above has an exit (attempts < 3) so it cannot spin endlessly.

Your turn

  1. Delete one of the ERROR lines from events. Which message prints now? Predict first.
  2. Change the while loop to give up after 2 attempts. What does it print at the end? (It will still say "Connected". Why is that misleading? This kind of subtle wrongness is what your tests, in C8, must catch.)
  3. Add a WARN counter alongside the error counter.

Lesson C3 in plain words

  • if / elif / else chooses a path. Indented lines belong to the block above them.
  • for repeats once per item. while repeats until a condition is false.
  • A counter starts at zero and grows as you find things.
  • An agent is a while loop with a model's decision inside. Always give it an exit.

Functions: the code behind a tool

By the end of this lesson you can:

  • explain the difference between return and print

The idea

A function is a named recipe. You define it once, give it inputs (called arguments), and it gives back a result. Then you can use it as often as you like. In Chapter 10 you designed tools with a name, a description, typed inputs and structured output. This lesson shows what that looks like in code: a tool is a function, and the "tool description" the model reads is just the function's name, inputs and short explanation.

  • The text in triple quotes right under the first line is a docstring: a description of what the function does. Frameworks (including MCP libraries) turn it into the tool description that the model reads.
Common mistake

print shows something to a human and the value is gone. return gives a value to the program so it can be used again. Tools must return their result, because the agent loop needs to pass it back to the model.

Errors, validation and JSON

By the end of this lesson you can:
  • reject bad input on purpose, and catch the problem instead of crashing
  • turn a dictionary into JSON text, and back again
  • explain why "errors are data" in an agent

The idea

In Chapter 11 you saw a tool call fail because a model passed a value the API did not accept. Models make odd requests: a server that does not exist, a missing field, a typo. A good tool does not crash. It checks its input and returns a clear error that the model can read and adjust to.

  • raise ValueError("message") deliberately signals a problem.
  • try: ... except ValueError as problem: ... says "try this, and if that kind of problem happens, do this instead". The program carries on.

The second idea is JSON. Models and programs exchange text. json.dumps(result) turns a dictionary into JSON text. json.loads(text) turns that text back into a dictionary. That conversion is the bridge between your tool and the model: the tool's result becomes text that goes into the model's context.

Watch it run

Step to the third server, WEB9. Watch the program jump out of the function, land in except, and carry on instead of crashing.

Line by line

  • import json brings in a tool kit that Python ships with for reading and writing JSON.
  • In test_sql_connectivity, the first check rejects any server whose name does not start with "EV". It raises an error rather than guessing.
  • reachable = server != "EV03" pretends EV03's SQL link is down (!= means "is not equal to"). The result uses None if reachable else "timeout after 15s", a compact way to say "no error if reachable, otherwise this message".
  • The loop tries three names. try calls the tool. For WEB9 the tool raises ValueError, and except builds a result dictionary describing the problem. The error became data with the same shape as a normal result.
  • json.dumps(result) converts it to text. Notice Python's True, False and None become JSON's true, false and null.
  • Finally json.loads(text) proves the text can be read back into a dictionary.
Why this matters for agents

From Chapter 11: errors go back to the model as data so it can adjust, and arguments are validated before anything runs. It is also the structured-result rule from Chapter 10: put parsing and validation in code. And from Chapter 12: unknown or malformed requests should be refused, not guessed at.

Lesson C5 in plain words

  • Validate inputs and raise an error for bad ones. Catch errors with try / except.

Classes: the state of an investigation

By the end of this lesson you can:

  • explain how a class can hold an agent's goal, evidence and hypothesis

The idea

So far, facts live in separate variables and actions live in separate functions. But an investigation is one thing: it has a goal, a growing list of evidence and a current hypothesis, and you do things to it (add evidence, print a report). A class bundles those together, like a case folder with a cover sheet and a set of standard procedures.

  • A class is a template. Writing Investigation("Why is indexing down?") makes one real folder from the template (an object).
  • __init__ runs once when the object is created and sets it up.
  • Variables that belong to the object are attributes, written self.goal. Functions that belong to it are methods.
  • self means "this particular object". It is always the first input of a method.

This is where agent state (Chapter 7) lives in real code. Frameworks do the same thing with larger state objects (for example, the LangGraph state in Chapter 13 that holds messages and the philosopher's context).

A pretend lab and a diagnosis loop

By the end of this lesson you can:
  • read a complete mini agent made of tools, history and a loop
  • find the single function where an AI model would go

The idea

Now combine everything: variables (C1), dictionaries (C2), loops and decisions (C3), functions as tools (C4). The result is a small Enterprise Vault diagnostic that behaves like the agent in Chapter 7, with one difference: its "brain" is a handful of rules, not an AI model. That is deliberate. You build the loop, the tools and the checks first, and make sure they work. Then replacing the rules with a model changes one function.

The pieces:

  • LAB is a dictionary that stands in for a real Enterprise Vault environment. It describes one failure: the service is stopped, the log shows a SQL timeout, SQL cannot be reached, DNS is fine.
  • Tools are four small functions that read from LAB. All read-only.
  • TOOLS is a dictionary mapping a tool's name to the function. This lets the loop call a tool by name, exactly as an agent does when a model says "call get_event_logs".
  • decide_next(history) looks at what has happened so far and picks the next tool, or returns None when it has seen enough.
  • history is a list recording each tool and its result.

Watch it run

This one is longer. Use Run to end if you want the overview first, then Restart and step through. Watch history grow and see which function the highlight visits at each turn.

Line by line

  • TOOLS = {"get_service_status": get_service_status, ...} stores the functions themselves (not the results of calling them) under their names.
  • decide_next reads the last tool and result. First time (history empty) it starts with the service status. If the status was Stopped it asks for the event logs. If the log mentions SQL it tests SQL. If SQL is unreachable it checks DNS. Otherwise it returns None.
  • while True: repeats forever, until break runs. The loop asks decide_next for a tool. If it is None, break leaves the loop.
  • result = TOOLS[tool]() looks up the function by name and calls it. The brackets at the end are what actually run it.
  • history.append((tool, result)) records the pair. A pair in round brackets is called a tuple: two things kept together.
An honest flaw to notice

The last line, print("Diagnosis: SQL server unreachable; DNS is fine."), is fixed text. It would print that even if the lab were different. The loop gathers evidence, but the conclusion is not computed from it. A tester would catch this at once: change LAB and the diagnosis is wrong. Lesson C8 teaches you to catch exactly this kind of bug, and the full starter agent in C11 fixes it by computing the answer.

Where the AI goes

Replace decide_next with a function that sends history to a language model and reads back which tool it wants. Nothing else changes: same tools, same loop, same history. That is the sentence "model proposes, software executes" in code. It is also why the step limit, the policy gate and the trace (C9) live in the loop and not in the model.

  • A mini agent is tools + history + a loop + a "decide next" function.
  • Calling a tool by name from a dictionary is how agent frameworks dispatch tool calls.
  • Build with rules first. Swap in a model later by replacing only decide_next.

Tests and measuring: your QA skills in code

By the end of this lesson you can:
  • write a small set of test scenarios with expected results
  • compute a pass rate and use assert as a regression alarm
  • explain how this becomes the evaluation harness for an agent

The idea

This is the lesson where you are already the expert. Chapter 9 said an agent needs a test set of reproducible failures with expected outcomes, a scorecard, and a regression suite. Testers do this every day. In code it is a list of cases, a loop that runs each one, and a comparison of actual to expected.

  • Each scenario is a dictionary: the conditions (service state, SQL, DNS) and the expected diagnosis.
  • The loop calls the function under test and compares its answer to the expectation: PASS or FAIL.
  • The task success rate is passes divided by total.
  • assert condition, "message" stops the program with an error if the condition is false. Put it at the end of a test run and any regression becomes impossible to miss.

Watch it run

Line by line

  • SCENARIOS is a list of three dictionaries. Each is a test case: the setup, plus "expect", the right answer.
  • diagnose(service, sql, dns) is the logic being tested. DNS failure first; then "stopped and SQL down"; otherwise it escalates to a human. (Note the third rule: it knows when to say I cannot tell. Chapter 9's "escalation rate" metric measures that.)
  • passed = passed + (1 if ok else 0) adds 1 for a pass. 1 if ok else 0 is a one-line decision.
  • {rate:.0%} inside an f-string formats a fraction as a percentage.
  • assert rate == 1.0, ... would crash the run with your message if any case failed. In a real project this runs every time you change anything.
From three cases to fifty

Your notes say to measure a diagnostic agent against 50 or more known failure scenarios, kept as a regression suite. This is the same program with more rows in SCENARIOS. The rows can come from your existing QA lab: every known failure mode you have reproduced becomes a case. Every time you improve the agent, you rerun the suite. If something that used to pass now fails, that is a regression.

Capability versus reliability

A rule-based diagnose gives the same answer every time, so a single run is enough. A language-model brain does not: run each scenario several times and report how often it succeeds every time (reliability, pass^k) as well as at least once (capability, pass@k). See reliability_demo.py in Chapter 9.

Traces and a policy gate

By the end of this lesson you can:
  • record a trace of what an agent did, one JSON line per step
  • write a gate that allows, denies or defers each tool call
  • explain "deny by default"

The idea

Two production habits from Chapters 12 and 13, in a few lines:

  • A policy gate. The model proposes a tool call; your code decides whether it may run. Read-only tools are allowed. Risky ones need human approval. Anything unknown is denied. Deny by default means a tool nobody thought about is blocked, not allowed.
  • A trace. A record of every proposal and decision, so when something goes wrong you can reconstruct what happened. We store each step as a small dictionary and print it as one line of JSON. Files of such lines are called JSON lines and are easy to search and replay.

Sets, written with curly brackets and no labels ({"a", "b"}), are handy for "is this tool in the allowed group?" checks.

Watch it run

Watch the trace list grow with each call, and see how verdict changes.

Line by line

  • READ_ONLY and NEEDS_APPROVAL are sets of tool names. They are the policy, kept in one visible place.
  • run_tool(name, human_ok=False) has a default for human_ok: if the caller does not say, it is False. A safe default.
  • The if / elif / else picks a verdict. The final else is the "deny by default" rule.
  • trace.append({...}) records the step number, the tool and the verdict. len(trace) + 1 numbers each entry.
  • The last two calls show the key behaviours. restart_service is denied without approval and allowed with it. delete_data is denied even with human_ok=True, because it is on no list at all. Some actions should never be available to an automated agent, whoever clicks approve.
  • The list comprehension [e["tool"] for e in trace if e["verdict"] == "deny"] is a short way to build a list: "the tool name of every entry whose verdict was deny".
Authorisation is policy

"The authorisation decision belongs to software policy, not model confidence." Notice that nothing in this code asks the model how sure it is. And because the gate sits in your loop, even a model that was tricked by prompt injection (Chapter 12) cannot call a tool the policy does not allow.

Lesson C9 in plain words

  • A gate checks every proposed tool call against policy. Unknown means deny.
  • A trace records each step as a line of JSON so you can reconstruct what happened.
  • The model proposes. Your code decides. Neither the gate nor the trace asks the model for permission.

1. Secrets: API keys do not belong in code

To call a real language model you need an API key: a long secret string that identifies and bills your account. Anyone who has it can spend your money. So the first rule: never type a key into a file that you might share, upload or paste into a chat. Instead, store it in an environment variable, a named setting held by your computer, and have the program read it:

import os

api_key = os.environ.get("ANTHROPIC_API_KEY")   # reads the setting; returns None if it is missing
if not api_key:
    print("Set the ANTHROPIC_API_KEY environment variable first.")
else:
    print("Key found (not printing it).")

In Windows PowerShell you can set it for the current window only (it disappears when you close it):

$env:ANTHROPIC_API_KEY = "paste-your-key-here"
python my_agent.py
  • Never paste the key into a chat, an issue, a screenshot or a Git repository.
  • If a key leaks, revoke it in your account and create a new one.
  • Use the narrowest permissions and spending limits your provider offers.

2. Describing a tool to a model

In Chapter 11 you saw that a model learns what tools exist from a description. That description is data, in JSON Schema form. For the C4 function it looks like this. It is the same information as the function's name, docstring and inputs, written for the model:

get_service_status_tool = {
    "name": "get_service_status",
    "description": "Return the state of one Windows service on one server. Read-only.",
    "input_schema": {
        "type": "object",
        "properties": {
            "server":  {"type": "string", "description": "Server name, for example EV01"},
            "service": {"type": "string", "description": "Service name, for example Indexing"},
        },
        "required": ["server", "service"],
    },
}

Good descriptions matter: they are the only thing the model knows about your tool. Write them for a stranger, then ask a model whether anything is ambiguous (Chapter 8).

3. Calling a real model

Chapter 11 shows the full loop. The shape is always: build the messages, send them with the tool descriptions, check whether the reply asks for a tool, run it yourself, send the result back, repeat. Your rule-based decide_next from C7 is replaced by that call. Everything else (tools, history, step limit, gate, trace) is the code you already have. Start with read-only tools and harmless data, and put a step limit and a cost limit in the loop before your first real run, because a loop that misbehaves spends real money.

4. Your tools as an MCP server

Chapter 10 explained MCP: write a server once and any compatible AI application can use it. With the official Python library the C4 function becomes a server almost unchanged. You add one line above the function (a "decorator", which registers it as a tool) and the library reads the name, the docstring and the typed inputs to build the schema for you:

# pip install mcp
from mcp.server.mcpserver import MCPServer

mcp = MCPServer("ev-diagnostics")

@mcp.tool()
def get_service_status(server: str, service: str) -> dict:
    """Return the state of one Windows service on one server. Read-only."""
    fake = {"Indexing": "Stopped", "Storage": "Running"}
    return {"server": server, "service": service,
            "status": fake.get(service, "Unknown"), "error": None}

if __name__ == "__main__":
    mcp.run()          # speaks MCP over standard input/output by default

"""Enterprise Vault diagnostic agent: a runnable starter (standard library only).

Parts, matching the course:
  Lab        a pretend environment with four failure scenarios (Chapter 9: a test set)
  tools      read-only functions (Chapters 6 and 10)
  gate       policy check before any tool runs (Chapter 12)
  brain      decides the next step. Rules today; swap in an LLM later (Chapters 7, 11)
  run_agent  the loop with a step limit and a trace (Chapters 7, 11, 13)
  evaluate   runs every scenario and scores the agent (Chapter 9)
"""
import json

SCENARIOS = {
    "sql_down": {"service": "Stopped", "events": ["09:12 ERROR SQL connection timeout"],
                 "sql": False, "dns": True, "root_cause": "SQL server unreachable"},
    "dns_broken": {"service": "Running", "events": ["10:40 WARN Name resolution failed for sql01"],
                   "sql": True, "dns": False, "root_cause": "DNS record for SQL host failing"},
    "stopped_unknown": {"service": "Stopped", "events": [],
                        "sql": True, "dns": True, "root_cause": "cause unclear: escalate to a human"},
    "all_good": {"service": "Running", "events": [],
                 "sql": True, "dns": True, "root_cause": "no fault found"},
}

class Lab:
    """A pretend environment. Each method is a read-only tool."""
    def __init__(self, scenario):
        self.s = scenario

    def get_service_status(self):
        return {"status": self.s["service"]}

    def get_event_logs(self):
        return {"lines": list(self.s["events"])}

    def test_sql_connectivity(self):
        return {"reachable": self.s["sql"]}

    def check_dns(self):
        return {"resolved": self.s["dns"]}

    def restart_service(self):                  # a WRITE tool: the gate must block it
        return {"restarted": True}

READ_ONLY = {"get_service_status", "get_event_logs", "test_sql_connectivity", "check_dns"}

def gate(tool):
    """Allow read-only tools. Everything else is denied (add human approval later)."""
    return "allow" if tool in READ_ONLY else "deny"

def brain(history):
    """Decide the next step from what has been seen so far. Returns (kind, value)."""
    seen = {tool: result for tool, result in history}
    if "get_service_status" not in seen:
        return "tool", "get_service_status"
    if "get_event_logs" not in seen:
        return "tool", "get_event_logs"
    service = seen["get_service_status"]["status"]
    lines = seen["get_event_logs"]["lines"]
    if any("Name resolution" in line for line in lines) and "check_dns" not in seen:
        return "tool", "check_dns"
    if any("SQL" in line for line in lines) and "test_sql_connectivity" not in seen:
        return "tool", "test_sql_connectivity"
    if "check_dns" in seen and not seen["check_dns"]["resolved"]:
        return "final", "DNS record for SQL host failing"
    if "test_sql_connectivity" in seen and not seen["test_sql_connectivity"]["reachable"]:
        return "final", "SQL server unreachable"
    if service == "Stopped":
        return "final", "cause unclear: escalate to a human"
    return "final", "no fault found"

def eager_brain(history):
    """A badly behaved brain: after diagnosing it tries to restart the service on its own."""
    kind, value = brain(history)
    if kind == "final" and not any(tool == "restart_service" for tool, _ in history):
        return "tool", "restart_service"
    return kind, value

def run_agent(lab, brain_fn=brain, max_steps=8):
    history, trace, denied = [], [], 0
    for step in range(1, max_steps + 1):
        kind, value = brain_fn(history)
        if kind == "final":
            trace.append({"step": step, "final": value})
            return value, trace, denied
        verdict = gate(value)
        trace.append({"step": step, "tool": value, "verdict": verdict})
        if verdict == "allow":
            history.append((value, getattr(lab, value)()))
        else:
            denied += 1
            history.append((value, {"error": "blocked by policy"}))
    return "step limit reached", trace, denied

def evaluate(brain_fn=brain):
    passed, total_steps, blocked = 0, 0, 0
    for name, scenario in SCENARIOS.items():
        answer, trace, denied = run_agent(Lab(scenario), brain_fn)
        ok = answer == scenario["root_cause"]
        passed += ok
        total_steps += len(trace)
        blocked += denied
        print(f"{'PASS' if ok else 'FAIL'}  {name:<16} steps={len(trace)}  answer={answer}")
    n = len(SCENARIOS)
    print(f"success {passed}/{n}  avg steps {total_steps / n:.1f}  blocked write attempts {blocked}")

if __name__ == "__main__":
    print("--- one run, with its trace ---")
    answer, trace, _ = run_agent(Lab(SCENARIOS["sql_down"]))
    for entry in trace:
        print(json.dumps(entry))
    print("Answer:", answer)
    print("\n--- evaluation: careful brain ---")
    evaluate(brain)
    print("\n--- evaluation: eager brain (tries to restart on its own) ---")
    evaluate(eager_brain)
