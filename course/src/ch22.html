Coding track · Lesson C7

A pretend lab and a diagnosis loop

By the end of this lesson you can:
  • read a complete mini agent made of tools, history and a loop
  • find the single function where an AI model would go
  • explain why building the rule-based version first is good engineering

The idea

Now combine everything: variables (C1), dictionaries (C2), loops and decisions (C3), functions as tools (C4). The result is a small Enterprise Vault diagnostic that behaves like the agent in Chapter 7, with one difference: its "brain" is a handful of rules, not an AI model. That is deliberate. You build the loop, the tools and the checks first, and make sure they work. Then replacing the rules with a model changes one function.

The pieces:

  • LAB is a dictionary that stands in for a real Enterprise Vault environment. It describes one failure: the service is stopped, the log shows a SQL timeout, SQL cannot be reached, DNS is fine.
  • Tools are four small functions that read from LAB. All read-only.
  • TOOLS is a dictionary mapping a tool's name to the function. This lets the loop call a tool by name, exactly as an agent does when a model says "call get_event_logs".
  • decide_next(history) looks at what has happened so far and picks the next tool, or returns None when it has seen enough.
  • history is a list recording each tool and its result.

Watch it run

This one is longer. Use Run to end if you want the overview first, then Restart and step through. Watch history grow and see which function the highlight visits at each turn.

Line by line

  • TOOLS = {"get_service_status": get_service_status, ...} stores the functions themselves (not the results of calling them) under their names.
  • decide_next reads the last tool and result. First time (history empty) it starts with the service status. If the status was Stopped it asks for the event logs. If the log mentions SQL it tests SQL. If SQL is unreachable it checks DNS. Otherwise it returns None.
  • while True: repeats forever, until break runs. The loop asks decide_next for a tool. If it is None, break leaves the loop.
  • result = TOOLS[tool]() looks up the function by name and calls it. The brackets at the end are what actually run it.
  • history.append((tool, result)) records the pair. A pair in round brackets is called a tuple: two things kept together.
An honest flaw to notice

The last line, print("Diagnosis: SQL server unreachable; DNS is fine."), is fixed text. It would print that even if the lab were different. The loop gathers evidence, but the conclusion is not computed from it. A tester would catch this at once: change LAB and the diagnosis is wrong. Lesson C8 teaches you to catch exactly this kind of bug, and the full starter agent in C11 fixes it by computing the answer.

Where the AI goes

Replace decide_next with a function that sends history to a language model and reads back which tool it wants. Nothing else changes: same tools, same loop, same history. That is the sentence "model proposes, software executes" in code. It is also why the step limit, the policy gate and the trace (C9) live in the loop and not in the model.

Lesson C7 in plain words

  • A mini agent is tools + history + a loop + a "decide next" function.
  • Calling a tool by name from a dictionary is how agent frameworks dispatch tool calls.
  • Build with rules first. Swap in a model later by replacing only decide_next.
  • A fixed conclusion that ignores the evidence is a bug that tests should catch.
