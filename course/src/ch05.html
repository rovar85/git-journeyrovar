How software talks to a model

When you use a chat website, you type text and get text back. Programs do the same through an API:

Your softwareBuilds the text of a request
→
Model providerRuns the model on powerful computers
→
Generated textReturns to your software
→
Your softwareReads the text and uses it, or sends another request

The input is free-form text, written in ordinary language. The text you send is called a prompt. Writing it well is called prompting, and it is the single biggest lever you have. The same model can give a poor or an excellent answer depending on the prompt.

A bigger idea

A prompt is not just one sentence telling the model what to do. It is the entire context you construct for one model call: system rules, the user's goal, examples, retrieved evidence, tool descriptions, previous observations, current state, and the required output format. Better prompting is often really better context construction.

So is better prompting always enough?

No. Some problems are limited by missing information or missing actions. No wording can make a model know today's weather or your company's refund policy. That is where retrieval and tools (Chapter 6) and agents (Chapter 7) come in. Better context plus tools plus repeated feedback beats a clever sentence.

Five habits of good prompts

Habit 1: be clear and detailed

The model cannot read your mind. "Write about our bottle" leaves it guessing the length, the audience, the tone and the facts. Say what you want.

Habit 2: show examples

Give one or two sample inputs and outputs in the style you want, then ask your real question. This is called few-shot prompting. Showing is often stronger than describing.

Habit 3: give it the facts

If the answer depends on specific information, paste that information in, and tell the model to use only that. Add "if the answer is not in the text, say you cannot find it". This cuts down hallucination a lot, and it is the seed of the technique in Chapter 6.

Habit 4: let it think before it answers

Asking for the answer immediately gives the model no room to work. Ask it to reason first. This is called chain of thought. A well-known case: ask a mid-sized model "is this student's maths solution correct?" and it may just agree. Ask it to first work out its own solution, then compare, and it checks properly. The written steps are part of the text the model reads when it produces the next words, so they genuinely help.

Habit 5: split big jobs into small steps

One prompt with five tasks often goes badly. Five prompts with one task each, where the output of each feeds the next, works better. This is called prompt chaining.

→
Prompt 2Outline using those facts
→

The context window is a budget

Everything in the "context" competes for the same limited space, the context window from Chapter 2. Longer context costs more and responds slower. When an agent runs for many steps, tool results and logs can swallow the window. Experiment with a budget. All sizes are in thousands of tokens and invented for the demonstration:

Context budget What fits in one call?

The practical lessons: summarise old conversation, retrieve only the few chunks you need, trim verbose tool output into the few fields that matter, and keep tool descriptions short and precise. Anthropic's engineers note that at each step an agent knows the world only through roughly the 10 to 20 thousand tokens in front of it. If something is not in the context, the model cannot use it.

Two engineering habits that beginners skip

  • Keep logs. Record the prompts you sent and the answers you got. When something goes wrong, the log is how you find out why. Later chapters call this observability.
  • Measure from the start. Make a small set of questions with the answers you expect, and score your system against it each time you change something. Humans can do the scoring, but that is slow and costly, so people often ask a second model to grade the answers. That is called LLM-as-a-judge. Models improve and get retired quickly. If you can measure, you can switch to a better model with confidence.

Also, version your prompts like code. A prompt gets edited many times, and you want to compare versions and go back. Chapter 13 shows how a real project does this.

A cost-saving trick: the router

Not every question needs the biggest model. A small piece of software (or a small model) can look at each incoming request and send it to the right prompt and the right model. Simple questions go to a cheap model. Hard ones go to a strong model. This lowers cost and often improves quality. You will meet the same idea as a "routing" workflow in Chapter 8.

Try it yourself (no code)

  1. Pick a real task from your own work. Write the laziest prompt you can and save the answer.
  2. Rewrite it using the five habits. Save the answer and compare the two.
  3. Ask the model: "Is anything in my prompt ambiguous? What would you need to know to do this better?" This "ask the model about the prompt" trick is used by experienced agent builders.

Chapter 5 in plain words

  • Software talks to a model by sending text and reading text back.
  • A prompt is the whole context you build for one call, not just one sentence.
  • Good prompts are clear, show examples, supply facts, allow thinking and split big jobs.
  • The context window is a finite budget. Manage it.
  • Keep logs, version prompts and measure results from the first day. A router can send easy requests to cheap models.
