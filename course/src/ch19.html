Coding track · Lesson C4

Functions: the code behind a tool

By the end of this lesson you can:
  • write a function with inputs and a returned result
  • explain the difference between return and print
  • see that an agent tool such as get_service_status is simply a function

The idea

A function is a named recipe. You define it once, give it inputs (called arguments), and it gives back a result. Then you can use it as often as you like. In Chapter 10 you designed tools with a name, a description, typed inputs and structured output. This lesson shows what that looks like in code: a tool is a function, and the "tool description" the model reads is just the function's name, inputs and short explanation.

  • def name(inputs): starts a definition. The indented lines below are the recipe.
  • return value hands a result back to whoever called the function and ends it.
  • The text in triple quotes right under the first line is a docstring: a description of what the function does. Frameworks (including MCP libraries) turn it into the tool description that the model reads.
Common mistake

print shows something to a human and the value is gone. return gives a value to the program so it can be used again. Tools must return their result, because the agent loop needs to pass it back to the model.

Watch it run

Notice how the highlight jumps up into the function when it is called, and how the Variables box then shows the function's own inputs under "in get_service_status()".

Line by line

  • def get_service_status(server, service): defines the tool. It takes two inputs. Defining a function does not run it. Python just remembers the recipe.
  • The dictionary known is a pretend lookup table (in real life this line would query Windows). known.get(service, "Unknown") looks up the service, and gives "Unknown" if it is not found, rather than crashing.
  • The function returns a dictionary with a fixed shape: server, service, status, error. A predictable shape makes a tool easy for a model to use and easy for you to test.
  • summarise(result) is a second function that turns a result into one readable line. Functions can use other functions' results.
  • The last three lines call the tool with different inputs. For "Search" the table has no entry, so the status is "Unknown". The tool handled it gracefully.
Design lessons you already know

Each tool has one job, typed inputs, structured output and an explicit way to report problems (here, "Unknown" and an error field). Those are the tool-design rules of Chapter 10, now visible as code. Notice also that this function only reads. Nothing about it changes any system.

Your turn

  1. Add a third entry to known, such as "Search": "Running". Call the tool for it. Predict, then run.
  2. Write a new function is_stopped(result) that returns True if the status is "Stopped". Test it on two results.
  3. Add a docstring to summarise. Why would a good docstring matter if a model were choosing between ten tools?

Lesson C4 in plain words

  • A function is a named recipe: def it once, call it many times.
  • return gives a value back. print only shows it.
  • A tool is a function with a clear job, predictable output and a docstring that describes it.
