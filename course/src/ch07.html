The progression: from prompt to agent

Agents are not a separate species. They are the end of a staircase that you have already climbed:

LevelWhat is addedShape
1A plain promptprompt → answer
2Context from your documents (RAG)prompt + retrieved text → answer
3Toolsthe model can call functions and see results
4A loop with a goalgoal → act → observe → decide again, until done
5Several specialised agentsan orchestrator and helpers

The model stays the reasoning core throughout. What changes is the system around it: it can retrieve, call functions, plan, reflect, remember and interact with an environment.

What is an agent?

Many definitions exist, and the speakers in your source talks each phrase it slightly differently. They agree on the shape:

  • "An LLM, memory, planning, tools and a while loop" (Kam Lasater).
  • "Models using tools in a loop", defined by three parts: the environment, a set of tools, and a system prompt (Barry Zhang, Anthropic).
  • "Language models control the operation of a system" (a definition Sayash Kapoor cites). By that standard even ChatGPT is a rudimentary agent: it filters inputs and outputs and can call tools.

A practical definition for building: an agent is a software system in which an LLM helps choose actions toward a goal, using tools and observations to decide what to do next.

Teacher says

The model is not the whole agent. The agent is the complete loop around the model: instructions, environment, tools, state, results and stopping rules. This is the fourth of the five diagrams to memorise: goal → model → tool → observation → state → model → … → done.

The reason-act loop (ReAct)

The core agentic pattern alternates deciding and doing: decide the next action → call a tool → observe the result → update your understanding → decide again. It is often called ReAct (reason and act). Reasoning gives the model a plan. Acting gets it new information from the outside world. Together they let a model solve problems that no single answer could.

Engineering note

For engineering you do not need to expose a model's hidden reasoning. What you need is the action and observation loop, short decision summaries, evidence and traceability. You must be able to see what it did and why.

Watch an agent work

Here is a worked example in the spirit of your study notes: an agent investigating "Why is Enterprise Vault indexing down?". It has read-only tools. At each step it sees only what is in its context, picks a tool, and learns from the result. All tool outputs are invented for the demonstration. Pick a scenario. Notice how the second one sends the agent down a different path because the observations are different. That is the point of an agent: the next step depends on what it found.

Planning

Planning means deciding what sequence of actions could reach the goal. Instead of you breaking the task into steps (like the prompt chaining of Chapter 5), you ask the model to break it down. Some agents plan once up front. Others re-plan as evidence arrives. Remember: a plan is a hypothesis about the environment, not reality. When a step fails, the agent must adapt.

Reflection

Reflection means making a draft, critiquing it against criteria, and producing a better version. The Stanford talk's example is refactoring code: first ask the model to read the code and give constructive feedback, then give the code and that feedback to a second call that rewrites it. It is quick to implement and often improves quality. The limit: reflection can improve a result, but it is not proof of correctness. A model can critique an answer and still miss the real defect.

Memory and state

An agent must keep track of where it is. "Memory" covers several different things:

KindMeaningExample
Working contextinformation in the current model callthe latest tool result
Task statewhere the current job standshypothesis: SQL timeout
Conversation memoryrecent interaction historythe user's earlier instruction
Long-term memoryinformation that persistsa known failure pattern
Episodic memorypast tasks and eventsa previous incident trace

Memory should be selective. Storing everything creates privacy, relevance and retrieval problems. A strong system decides what is worth remembering and how it will be retrieved. Chapter 13 shows short-term and long-term memory in a real project.

Many agents

One design splits the work among specialist agents: an orchestrator hands tasks to a documentation agent, a database agent and a testing agent, then synthesises their results. Benefits: separation of concerns, parallel work, and protecting the main agent's context window. Costs: every extra agent adds another context, another failure surface, more messages and more money. Stanford presents specialised agents as one pattern. Anthropic discusses multi-agent collaboration as an emerging direction while insisting on simplicity first. Open question from Barry Zhang's talk: how do agents talk to each other asynchronously, instead of in rigid user-assistant turns?

Why not always build the most autonomous agent?

Because every bit of autonomy adds cost, delay and the consequences of mistakes. You choose the smallest architecture that reliably delivers the value. Chapter 8 gives you a rubric for this.

Chapter 7 in plain words

  • An agent is a model using tools in a loop toward a goal. The model is not the whole agent.
  • Chatbot answers, workflow follows your fixed steps, agent decides the steps. Start with the simplest that works.
  • ReAct: decide, act, observe, update, repeat. Planning, reflection and memory strengthen it.
  • More agents means more power and more cost, failure points and complexity.
