This chapter follows Barry Zhang of Anthropic, who gives three ideas: don't build agents for everything, keep it simple, and think like your agent. We add the workflow patterns from the Anthropic article "Building Effective Agents" that your study notes cite.

How we got here

Most teams start with single-call features such as summarisation, classification and extraction. Then one call is not enough, so they orchestrate several calls in a predefined flow. That trades cost and delay for better performance. These are workflows. Models are now capable enough that agents are appearing in production: unlike workflows, agents decide their own trajectory and act almost independently, guided by feedback from the environment. The trend is clear. The more agency you give a system, the more useful it can be. But cost, delay and the consequences of errors go up with it.

Idea 1: don't build agents for everything

Agents are a way to scale complex and valuable tasks. They should not be a drop-in upgrade for every use case. Ask four questions:

  1. Is the task complex and ambiguous? Agents thrive in ambiguous problem spaces. If you can map the whole decision tree easily, build that explicitly and optimise each node. It is cheaper and gives you more control.
  2. Is the task valuable? Exploration costs a lot of tokens. If your budget is around 10 cents per task, for example in a high-volume customer-support system, that affords only roughly 30,000 to 50,000 tokens. Use a workflow for the common cases.
  3. Have you de-risked the critical capabilities? For a coding agent: can it write good code, debug, and recover from errors? Bottlenecks are not fatal but multiply cost and delay. If you find some, narrow the scope and try again.
  4. What is the cost of an error, and how easily is it discovered? If errors are high-stakes and hard to spot, you cannot trust an agent to act for you. You can limit the damage with read-only access and human approval, but that also limits how far you can scale.

Coding is a good example. Going from a design document to a pull request is ambiguous and complex. Good code is valuable. Models are already strong at many parts of the coding workflow. And output is easy to verify with unit tests and CI. That is why coding agents lead the way.

Token budget Does an exploring agent fit in the budget?

The price is an assumption you can change. The talk's figure (10 cents buys 30,000 to 50,000 tokens) corresponds to a blended price of roughly $2 to $3 per million tokens. Real prices vary by model, and input and output tokens are priced differently.

Idea 2: keep it as simple as possible

Anthropic's view of an agent is "models using tools in a loop", and three components define it:

Environmentthe system the agent operates in
Toolsthe interface for acting and getting feedback
System promptgoals, constraints and ideal behaviour
→
The model, called in a loop

Their lesson, learned the hard way: complexity up front kills iteration speed. Three very different agents they built (coding, computer use, search) share almost exactly the same code. The environment depends on your use case, so your only real design decisions are the set of tools and the prompt. Iterate on those first. It gives by far the best return. Optimise later:

  • For coding and computer use: cache the trajectory to cut cost.
  • For search, which makes many tool calls: run calls in parallel to cut delay.
  • For almost everything: show the agent's progress so users trust it.

Idea 3: think like your agent

Builders, Barry included, develop agents from their own perspective and are confused when the agent errs. The fix: put yourself in the agent's context window. An agent can look very sophisticated, but at every step the model is just running inference on a limited set of tokens, around 10 to 20 thousand. Everything it knows about the world is in there.

Imagine being a computer-use agent. You receive one still screenshot and a vaguely written description. You choose a click. While the click executes and the next screenshot is prepared, it is as if you closed your eyes for three to five seconds and used the computer in the dark. Then you open your eyes, and whatever you did may have worked, or may have shut the machine down. You quickly see what the agent would have needed: the screen resolution, recommended actions, the limits, and guardrails that stop wasted exploration.

The debugging question

"If I were the agent, with exactly this context and these tools, would the next decision be obvious?" Try the whole task from the agent's seat. It is a fascinating, mildly uncomfortable exercise.

Since the systems speak your language, you can also use them to help:

  • Paste your system prompt and ask: "Is any of this instruction ambiguous? Can you follow it?"
  • Paste a tool description and ask whether the agent would know how to use the tool, or wants more or fewer parameters.
  • Paste the agent's whole trajectory and ask: "Why did you make this decision here? What would help you decide better?"

This shouldn't replace your own understanding of the context, but it brings you closer to how the agent sees the world.

Three open questions (from the talk)

  • Budget-aware agents. Workflows have predictable cost and latency. Agents do not. How should we define and enforce budgets in time, money and tokens?
  • Self-evolving tools. Models already help refine tool descriptions. Could agents design and improve their own tools?
  • Multi-agent collaboration. Sub-agents protect the main agent's context and parallelise well. But how do agents communicate asynchronously and recognise each other's roles?

Notice how these connect to what you have learned: budgets (Chapter 5), tool design and discovery (Chapter 10), multi-agent protocols and security (Chapters 10 and 12).

The engineering judgement

The skill is not "build more agents". The skill is choosing the smallest architecture that reliably delivers the value.

Try it yourself (no code)

  1. Take the Enterprise Vault tool list from Chapter 7 (service status, event logs, SQL test, DNS check). Write the shortest possible system prompt for the diagnosing agent.
  2. Now sit in the agent's seat. At step 1 what does it not know? (For example: which server? What counts as "down"? What is it allowed to touch?) Add those answers to the prompt.
  3. Write a one-sentence description for each tool that would let a stranger use it correctly. Ask a model if any is ambiguous.

Chapter 8 in plain words

  • More agency means more usefulness and also more cost, delay and risk.
  • Build an agent only for complex, valuable tasks with de-risked capabilities and manageable error costs. Otherwise use a workflow.
  • A simple agent is environment + tools + system prompt, in a loop. Iterate on tools and prompt first, optimise later.
  • Five workflow patterns: prompt chaining, routing, parallelisation, orchestrator-workers, evaluator-optimiser.
  • Debug by thinking like the agent: what is in its context and tools right now?
