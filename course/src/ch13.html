From demo to production: PhiloAgents

By the end of this chapter you can:
  • describe how a single model call grows into a complete agent application
  • read a LangGraph-style workflow: nodes, edges, conditional edges and state
  • explain short-term and long-term memory, and why WebSockets suit real-time agents

PhiloAgents is an open-source course by Miguel Otero Pedrido and Paul Iusztin (their GitHub organisation is called Neural Maze). It builds a game village where every non-player character is an AI agent playing a historical thinker: Plato, Aristotle, Socrates, Turing, Ada Lovelace and others. You walk up, press a key, and have a conversation. It is a game, but it is also a compact example of a real agent application. That is why it is in this course: the educational value is architectural. You can see exactly how one LLM call becomes an application with state, retrieval, serving and observability.

The brain: a LangGraph workflow

A graph workflow describes an agent as nodes (steps that do work) joined by edges (which step comes next). Some edges are conditional: the next step depends on a decision. All the nodes share a state that is passed along and updated. In PhiloAgents the state is the list of messages plus extra fields: the philosopher's context, name, perspective, style, and a summary of the conversation so far.

The graph has five working nodes:

  • conversation: the model replies in character, using a prompt built from the philosopher's name, perspective and style. It can also decide to call a tool.
  • retrieve philosopher context: a retrieval tool that searches the long-term memory (a vector database).
  • summarise context: compresses what was retrieved, to avoid wasting tokens.
  • connector: a "do nothing" node used only to join paths.
  • summarise conversation: once the chat is long (more than 30 messages), it compresses the history.

The clever part is agentic RAG. A single conditional edge after the conversation node decides: does the model want to call the retrieval tool? If yes, go retrieve, summarise, and come back to the conversation node (a loop). If no, move on. The authors point out this takes only about five lines of code. Ask Turing "hello" and it just answers. Ask about the Chinese room argument and it fetches background first. The agent decides when it needs retrieval. That is the difference from plain RAG, which always retrieves. Run a conversation through the graph:

Two engineering choices to notice. First, the project uses different models for different jobs: a large model (Llama 3.3 70B on Groq) for the in-character conversation, and a smaller, faster one (Llama 3.1 8B) for the summaries. That is the router idea from Chapters 5 and 8. Second, the prompts are templates filled from a small data object per philosopher, so adding a new character is mostly adding data.

Memory: short-term and long-term

These two are very different. Short-term memory is the chat history, stored in the graph's state and saved to a database after each step (a checkpointer). Each philosopher has its own conversation thread ID, so Turing and Socrates never mix their histories. Long-term memory is the vector store of grounded knowledge: biographies and ideas, which makes answers historically accurate. How is long-term memory built? An offline pipeline downloads text about each philosopher from Wikipedia and the Stanford Encyclopedia of Philosophy, splits it into overlapping chunks, removes near-duplicates (using a similarity fingerprint), turns each chunk into an embedding, and stores it in MongoDB, which has vector search. At run time the retrieval tool uses a hybrid search, as Chapter 6 suggested. Everything from Chapter 6 shows up here in production form.

WebSockets: a persistent, two-way connection

A normal web request (HTTP) works like sending letters: the client opens a connection, asks, waits for the whole answer, and closes. For a real-time game that is a bottleneck. A WebSocket does one handshake and then keeps the connection open, so both sides can send messages whenever they like. The three advantages the authors list: low delay (no new connection per message), real-time two-way interaction, and room to scale to multiplayer. The server also streams the answer in chunks, and the game builds the text as it arrives. (An idle connection is closed after a timeout.) Compare them:

The Python server side is under 200 lines using FastAPI. It has an HTTP endpoint (handy for debugging) and a WebSocket endpoint that accepts the connection, receives JSON, calls the graph, and sends each chunk back. The game side is a JavaScript game built with Phaser, with a small service class to open and manage the connection.

Prompt versioning

We version code, data and models. Prompts deserve the same. A complex prompt, like the philosopher character card, is edited many times, and the project's card had 18 versions. Versioning lets you compare, see progress, and fall back. In the project each prompt is registered with a name, and whenever the text changes a new version is created automatically. Try it:

Observability: reconstruct what happened

Every conversation produces a trace: the sequence of steps (spans) with inputs, outputs, tokens used and time taken. You can see whether a tool was called and how long each step took. Evaluation: the five metrics and the test data

As Chapter 9 said, many people build RAG systems but few evaluate them. Here is how this project does it. A language model reads chunks from Wikipedia and the Stanford Encyclopedia and generates realistic multi-turn conversations between a user and a philosopher, grounded in those chunks (and a validation step checks that the format is right). Those conversations form the test set. To evaluate, the agent receives the messages up to the last assistant message, produces its own reply, and the system scores it against the expected one using five metrics, judged by another language model:

MetricRange and meaning
Hallucination0 to 1. 1 means the answer is fully grounded in the context.
Answer relevance0 to 1. 1 means the answer is relevant to the question and context.
Moderation0 to 1. Is the content toxic or offensive?
Context precisionWhat share of the retrieved context was relevant?
Context recallWhat share of all the relevant context was retrieved?

In the lesson's example run, scores were around 0.9 for relevance, 0.84 for hallucination (higher is better here), 0.65 for precision and 0.73 for recall. One conversation scored low on moderation (0.3) because the philosopher was defending free speech. The authors call that judgement a bit dumb. The judge is a tool you check, not an oracle. The lesson also warns that generating the test data is slow and uses many tokens, so a ready-made dataset is provided.

Code organisation

The Python backend uses clean architecture with three layers: a domain layer (the core concepts such as the philosopher object, the prompts and exceptions), an application layer (use cases, such as the conversation service and evaluation), and an infrastructure layer (the connections to the outside: the API, the database, the tracing tool). Keeping the layers apart makes each part easier to change and test.

Try it yourself (a real project)

If you have Git, Docker and a few free API keys, clone the PhiloAgents repository (search for "philoagents-course" in the Neural Maze GitHub organisation) and follow its install guide. The course says it runs locally with a single command that starts three services: the database, the agent API and the game. Then:

  1. Play for ten minutes. Ask Turing a casual question and then a specific one. Watch the difference in the traces.
  2. Open the graph in LangGraph Studio and find the conditional edge that implements agentic RAG.
  3. Change the character prompt for one philosopher, and see the prompt version increase.
  4. Run the evaluation and read the five metrics. Which is lowest? What would you change to improve it?

I have not run that project myself. Setup details can change, so follow the repository's own instructions.

Chapter 13 in plain words

  • A production agent is a stack: UI, API, agent graph, tools and retrieval, memory, an LLM gateway, observability and evaluation.
  • A graph workflow has nodes, edges, conditional edges and shared state. A conditional edge can implement agentic RAG: the agent decides when to retrieve.
  • Short-term memory is chat history in saved state. Long-term memory is a vector store built offline.
  • WebSockets keep a connection open for real-time, two-way streaming.
  • LLMOps: version prompts, trace everything, and evaluate with a test set and several metrics. Check the judge.
