Chapter 11

Build an agent from scratch

By the end of this chapter you can:
  • write (or read) the smallest working agent loop
  • explain each piece: model call, done-check, tools, parallel calls, planning, limits
  • run a complete agent on your own computer and extend it

Kam Lasater's talk has three goals: let you experience the simplest version of an agent, make you comfortable running and reading the code ("execution and decoding are a very important part of learning"), and give you intuition for how agent frameworks work, so that if you use one, you understand the parts underneath. This chapter follows his five steps, then gives you a program you can run.

Rule for the whole course

Understand first, code second, framework third. If code is new to you, work through the coding track (lessons C0 to C11) after Chapter 14, then come back here. You do not need to write code to read this chapter. The code is there so the ideas become concrete. If you do run it, you will understand agents far better than someone who only read about them.

What is an agent, in the smallest terms?

Two definitions Lasater likes: an agent is "LLM, memory, planning, tools, and a while loop." Break it down: memory is just reading and writing some state. The while loop is a condition plus a repeat. Rearrange those parts and you get a plan for the code.

Five steps, each adding one ability

Step through the build. At each step note what is new. Lasater observes that the first steps feel mechanical and deterministic, like ordinary code. The feeling changes at step 4, when you feel you are playing with an agent.

Build-up

The raw loop, in a few lines

Strip away the details and the whole thing is this. Your study notes call it the foundation of many agents:

messages = [system_prompt, user_goal]

while True:
    response = call_llm(messages)

    if response.requests_tool:
        result = execute_safe_tool(response.tool_name, response.arguments)
        messages.append(response)       # what the model asked for
        messages.append(result)         # what actually happened
        continue                        # go round again with the new information

    return response.text                # no tool requested: this is the answer

Frameworks later add persistence, streaming, retries, graphs, human approval and observability. The underlying alternating pattern, model proposes, software executes, result goes back, remains.

Tool calling in slow motion

→
LLM"I need service state."
→
Toolget_service_status
→
ResultSTOPPED
→
LLMupdates hypothesis, picks get_event_logs

Notice the key point: the model did not need to know the answer at the start. It gathered evidence, updated its working state and chose another action. Agent behaviour emerges from the combination of language model plus environment.

One more habit from Lasater: think of a tool as a text transformation. There may be a few parameters, but at heart most tools turn some input text into some output text. That makes them easy to reason about and test.

Make tool results structured

Do not make the model read enormous terminal output when your tool can pull out the fields that matter:

{
  "server": "EV01",
  "service": "Enterprise Vault Indexing Service",
  "status": "Stopped",
  "error": null,
  "checked_at": "2026-10-05T09:14:00Z"
}
Engineering rule

Put parsing and deterministic validation in code. Use the model for interpretation and for decisions that need language or context. Structured results improve reliability, evaluation and debugging.

Safety rails every loop needs

  • A step limit. An agent can loop forever without converging. Lasater mentions that real systems cap the number of iterations before the client code cuts it off.
  • A budget. Cap tokens and money too (Chapter 8's open question).
  • Errors are data. In his demo, a tool call failed because the model passed a location string that did not match what the search API accepts. Return errors to the model as results and let it adjust, but also validate arguments against the tool's schema before running.
  • Never run model output as code directly. The example calculator below parses only numbers and + − × ÷. It never uses eval.
  • Log a trace. Print every step. You will want to reconstruct the trajectory when something fails (Chapters 9 and 13).

The complete program (runs offline)

Here is a full agent in about a hundred lines, with all five abilities: planning with a to-do list, tools (search, calculator, the to-do tools), parallel tool calls, a "done?" judge, and a step limit. The language model is replaced by MockLLM, a small rule-based stand-in, so it runs with no account and no internet. Everything else is real agent code. It is saved as course/examples/mini_agent.py.

Run it with python mini_agent.py. You should see seven steps: it plans, searches twice in parallel, calculates, ticks off each to-do, and the judge accepts the final answer.

Swap in a real model (optional)

Only MockLLM.chat() is fake. To use a real model, you replace it with a call to a provider's API that supports tool calling. Here is the shape of that loop using Anthropic's Python SDK. I could not run this one here because it needs an API key and network access, so treat it as a starting sketch and check the current SDK documentation. 

import anthropic, json
client = anthropic.Anthropic()          # reads ANTHROPIC_API_KEY from the environment
MODEL = "put-a-current-model-name-here"

TOOL_SPECS = [{
    "name": "calculator",
    "description": "Evaluate simple arithmetic such as '(25 + 40) * 2'. Returns the numeric value.",
    "input_schema": {"type": "object",
                     "properties": {"expression": {"type": "string"}},
                     "required": ["expression"]},
}]   # add one entry per tool, using the TOOLS dictionary from mini_agent.py

def real_agent(goal, max_steps=12):
    messages = [{"role": "user", "content": goal}]
    for _ in range(max_steps):
        resp = client.messages.create(model=MODEL, max_tokens=1024,
                                      system="Plan with the to-do list first.",
                                      tools=TOOL_SPECS, messages=messages)
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":             # no tool requested: final answer
            return "".join(b.text for b in resp.content if b.type == "text")
        results = []
        for block in resp.content:
            if block.type == "tool_use":               # the model proposes...
                out = json.dumps(TOOLS[block.name](**block.input))   # ...your code executes
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": out})
        messages.append({"role": "user", "content": results})
    return "Stopped: step limit reached."

Notice what stayed the same: the loop, the tools, the step limit. Only the "brain" changed. Lasater suggests the next improvement is memory: save the pages the agent browses into a vector database so it can retrieve them later (RAG, Chapter 6).

Exercises (do at least two)

  1. Run it, then read the trace and match every line to a part of the loop.
  2. Add a tool called get_time() that returns today's date. Why might an agent need it? (Lasater added today's date to his prompt because models can be unsure what day it is.)
  3. Break it on purpose. Make search return "no results" for everything. Does the loop recover or spin? Lower max_steps to 3 and watch the safety rail work.
  4. Add a budget. Count the characters of every message and stop with an error when a limit is crossed.
  5. Design for Enterprise Vault. Replace search with three read-only tools that return fake JSON (get_service_status, get_event_logs, test_sql_connectivity) and let the mock "diagnose" a stopped service. This is the skeleton of Chapter 14.

Chapter 11 in plain words

  • An agent is a model call in a loop with tools, memory and planning.
  • Build it up: one call, a done-check, a tool, parallel tools, a to-do list for planning.
  • The model proposes tool calls. Your code executes them and returns structured results.
  • Add a step limit, a budget, error handling and a trace. Never run model output blindly.
  • Frameworks are this loop plus conveniences. Understanding the loop is what matters.
