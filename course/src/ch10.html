Why MCP exists

The motivation, in the words of Mahesh Murag of Anthropic: models are only as good as the context we give them. A year or so ago you copy-pasted context into chatbots. Then applications began giving models hooks into your data and tools, making them more powerful and personal. But every application built its own integration with every service. If there are N applications and M tools you get N × M custom connections.

The Model Context Protocol is an open protocol that standardises how AI applications connect to tools and data. It was inspired by two earlier standards. APIs standardised how web front ends talk to back ends. The Language Server Protocol (LSP) standardised how code editors talk to language-specific tools: build a Go language server once, and every LSP-compatible editor can use it.

Benefits: application developers connect any MCP server with no extra work. Tool and API providers build a server once and see adoption everywhere. Users get more context-rich applications. Enterprises get a clean way to separate teams: one team can own the vector-database server (like a microservice) and everyone else builds on it without asking permission each time.

Do not confuse them

MCP is not the model. MCP is not the agent loop. MCP is a protocol layer for connecting AI applications to external capabilities and context. The model and the loop live elsewhere.

The three primitives, and who controls each

A server can offer three kinds of things. The key idea is a clean separation of who decides when each is used:

PrimitiveControlled byWhat it isEnterprise Vault example
Toolthe modelan action the model chooses to callcollect_dtrace(EV01, Indexing)
Resourcethe applicationdata the app can attach: files, JSON, images, dynamic infoattach a troubleshooting document
Promptthe usera reusable template the user selects, like a slash command/investigate-indexing-failure
  • Tools are the most familiar: read tools to retrieve data, write tools to take actions, tools that update databases or write files. The server describes them, and the model decides when to call them.
  • Resources let the application, not the model, decide what to attach. In Claude Desktop they appear as attachments the user can click. Resources can be static, or dynamic (the server builds them from context). Clients can subscribe, so the server notifies them when a resource changes.
  • Prompts are templates packaged by whoever knows the domain. In the Zed editor, a slash command with a pull-request ID expands into a long predefined prompt. Teams use prompts for document Q&A and formatting rules.

Why not represent everything as a tool?

Because MCP coordinates the model, the application and the user. The application may need to attach data deterministically, and a human may need to explicitly choose a reusable prompt. Not every interaction should become a model decision. Also, if a call is predetermined (you always want the vector database searched), you do not need a tool at all: just call it. Tools shine when it is ambiguous whether to call. Murag's advice for beginners: start with tools, then add prompts and resources.

How MCP fits with agents

Recall the "augmented LLM" from Anthropic's article: a model with arrows to retrieval, tools and memory, run in a loop. MCP provides that whole bottom layer in a standard way. This means you do not need to build every capability in advance. The agent can discover new ones, even after it starts running. As the agent builder you can focus on the loop, context management, memory, and which model to use.

In the workshop's demo, a research task used a small open-source framework. It declared three sub-agents (a web researcher, a fact-checker and a report writer), gave each some ready-made MCP servers (a web-search server, a fetch server and a file-system server), and let an orchestrator plan and delegate. The whole thing was about 80 lines, and none of the servers were written by the builder.

So MCP does not replace agent frameworks. The framework manages the control loop and state. MCP gives a common way to discover and use external capabilities. Frameworks such as LangGraph have released adapters for exactly this reason.

Designing a good tool (the most important MCP skill)

A good tool is narrow, explicit and predictable. Its name describes the action, its inputs are validated and its output is structured. Compare:

Tool design checker Tick the properties a tool has and see what you get

A weak tool

name: run_check description: checks stuff inputs: text (string) output: (a huge block of raw terminal text)

A good tool

name: get_service_status description: Returns the state of one Windows service on one server. Read-only. inputs: server: string (e.g. "EV01") service: string output: status: string start_type: string error: string | null
Engineering rule

Put parsing and deterministic validation in code. Use the model for interpretation and for decisions that genuinely need language and context. Do not make the model read pages of terminal output when your tool can extract the few fields that matter. Structured results improve reliability, evaluation and debugging.

How many tools can an agent handle?

In the workshop's experience, current models cope well with about 50 to 100 tools, and Claude with a couple of hundred. Beyond that, long tool lists swamp the context. Ideas: a tool that searches tools (RAG over the tool library), or hierarchical groups of tools exposed progressively (finance tools, read tools, write tools). Tool names can also clash across servers, so namespacing is an open topic.

Advanced ideas from the workshop

  • Sampling. A server can ask the client to run a model call for it, instead of hosting its own model. The client keeps control over which model is used, the cost and privacy, and may refuse a suspicious request.
  • Composability. "Client" and "server" are logical roles, not physical machines. An agent can be a server to one application and a client of other servers, which allows layered systems where each layer specialises. Compounding errors and permissions need managing at each layer.
  • Registries and discovery. A central place to find, verify and version servers, similar to package registries. A "well-known" address on a company's website could advertise its official server. Combined with a registry, agents could find tools they were never programmed with, which the speaker called self-evolving agents. This also raises trust questions: you must decide which servers an agent may use.
  • Remote servers and authorisation. Early servers ran locally. Remote servers need identity and permission. The workshop described OAuth 2.0, where the server handles the sign-in handshake with the service and holds the token, while the client gets a session token.
  • Where logic belongs. Murag's opinion: retry logic and similar business logic are best on the server, because it is closest to the real system and clients may never have seen it before.
  • Tool annotations. Extra metadata, such as whether a tool only reads or also writes, so a client knows how risky a call is.

Security and trust for MCP

Once a server is remote, the problem becomes distributed systems and security: identity, authorisation, trust boundaries, rate limits, audit logs and least privilege. Four questions to ask of every tool call:

WHOcan call it?
WHATcan they call?
WHEREcan it act?
WHAT GETS LOGGED?
Governance

Never assume a tool is safe just because the model requested it. The authorisation decision belongs to software policy, not to model confidence. Chapter 12 builds on this.

MCP keeps changing: check the current specification

The workshop you watched was recorded in early 2025, and it said openly that many parts were still evolving (remote servers, stateful versus stateless connections, streaming, registries). Your study notes add that a later specification revision (dated 28 July 2026 in the notes) changed the protocol core, moving toward a stateless request-and-response design, and moved or deprecated some features. I could not verify that claim, so treat it as something to check. The safe learning rule from your notes is a good one: learn the concepts and design philosophy from this chapter, but implement new servers against the current specification and SDK documentation, not by copying old transport or lifecycle snippets.

Chapter 10 in plain words

  • MCP is an open standard so each tool is wrapped once (a server) and any compatible application (a host with a client) can use it. It flattens the N × M integration problem.
  • Three primitives: tools (model-controlled), resources (application-controlled), prompts (user-controlled).
  • MCP complements agent frameworks. It supplies capabilities, and the framework runs the loop.
  • Good tools are narrow, validated and return structured output. Start read-only.
  • Authorisation is a software policy decision. Ask who, what, where and what gets logged.
  • The protocol evolves. Implement against the current specification.
