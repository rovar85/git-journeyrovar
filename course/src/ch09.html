Chapter 9

Evaluating agents

By the end of this chapter you can:
  • explain why evaluating agents is harder than evaluating language models
  • distinguish capability from reliability, and compute both
  • explain why cost must be a metric, and how to read a cost-accuracy chart
  • design a scorecard and a test set for an agent
Why this chapter matters most

Anyone can make an impressive demo. The engineering skill is measuring whether it works, every time, at an acceptable cost. Sayash Kapoor's talk, which this chapter follows, argues that building agents is closer to reliability engineering than to ordinary software or machine learning work.

Reason 1: agents are hard to evaluate, and the failures are public

Kapoor opens with real cases where claims about agents did not hold up. These are his reports. Read them as lessons in what to check, not as rulings on any company:

  • A "robot lawyer" startup claimed to automate a lawyer's work and was later fined by the US Federal Trade Commission, because its claims about effectiveness were false.
  • Leading legal-research AI products advertised as preventing hallucinations were tested by Stanford researchers, who found hallucinations in at least about one answer in six, including invented paragraphs and distorted legal text.
  • "AI scientist" claims. His team built a benchmark called CORE-Bench, where an agent is given a paper's code and data and must only reproduce the results, far easier than automating science. The best agents reproduced fewer than about 40 percent. The "AI scientist" had been tested on toy tasks, with another language model, not human experts, doing the judging.
  • An optimisation claim that could not be true. A company announced an agent that made GPU code about 150 times faster. On inspection, the claimed speed exceeded the hardware's theoretical maximum by around 30 times. The agent had most likely gamed the scoring instead of doing the task.
Reward hacking

If an agent optimises the scoring mechanism rather than the underlying task, a high score can be evidence of exploiting the benchmark, not of real ability. Always ask what exactly the score measures and how it could be cheated.

Reason 2: static benchmarks mislead for agents

  • Agents act in the world. A language model can be judged on input and output text. An agent needs an environment to act in, which is much harder to build.
  • No natural ceiling on cost. A model call is bounded by its context window. An agent can loop, spawn sub-agents and call tools without limit. So cost must be a metric next to accuracy, or you will not see how well the agent really performs.
  • Agents are specialised. A coding agent cannot be judged on a web-browsing benchmark. You need multi-dimensional measures, not one score.
  • Benchmarks are not reality. Kapoor cites a coding agent that raised large funding partly on a benchmark. When a team used it on 20 real tasks for a month, only 3 succeeded.

Cost matters: read a Pareto chart

If you plot agents by cost and accuracy, the interesting ones sit on the Pareto frontier: you cannot get a better result without paying more. Kapoor's example: two agents with about the same accuracy where one cost about $57 and the other about $664. The choice is easy. Below is an illustrative chart (invented numbers). Some people ask: "Are models becoming too cheap to measure?" Prices have fallen by more than a hundred times for comparable ability over a few years. But applications that scale are still costly, prototyping with loose spending can run into thousands of dollars, and the Jevons paradox suggests cheaper calls lead to more calls, so total spend can rise. (The paradox: when coal became cheaper to use, total coal use went up, not down.)

Reason 3: capability is not reliability

Capability is what a system can do at least some of the time. Technically it is "pass at k" for large k: one of k attempts is correct. Reliability is doing it correctly every time. Language models are already capable of many things. A product needs reliability. If a personal assistant orders your food correctly 80 percent of the time, that is a catastrophic product failure, not a good demo. Compute it yourself:

Capability versus reliability assumes attempts are independent

Going from 90 percent to the "five nines" of reliability (99.999 percent) is not a matter of more of the same training. Kapoor's argument: ML engineers get you to about 90 percent. Closing the gap beyond that is the AI engineer's job.

A mindset shift

When the ENIAC computer had 17,000 vacuum tubes that failed so often it was unavailable about half the time, engineers' main job for two years was making it reliable enough to use. Kapoor says AI engineers should see their job the same way: not to build perfect products, but to remove the reliability problems of stochastic components. It is a system design problem.

One proposed fix is a verifier, like a unit test, that checks the agent's output. Useful, but verifiers are imperfect too. Two well-known coding benchmarks had tests with false positives, where wrong code still passes. When false positives are included, trying more attempts can make results worse, because more attempts find more ways to fool the test.

Capability and reliability in code (optional)

This script simulates it. The numbers it prints match the formulas above. (Saved as course/examples/reliability_demo.py.)

import random

def evaluate(p, tasks=2000, trials=5, seed=1):
    rng = random.Random(seed)
    any_ok = all_ok = 0
    for _ in range(tasks):
        results = [rng.random() < p for _ in range(trials)]
        any_ok += any(results)   # pass@k: at least one attempt worked
        all_ok += all(results)   # pass^k: every attempt worked
    return any_ok / tasks, all_ok / tasks

for p in (0.6, 0.8, 0.95, 0.99):
    cap, rel = evaluate(p)
    print(f"p={p:.2f}  pass@5={cap:.3f}  pass^5={rel:.3f}")

A scorecard has many dimensions

A production scorecard for an agent should contain several measurements, not a single score. Kapoor argues for task-appropriate, multi-dimensional evaluation. Your study notes suggest this set for a diagnostic agent:

MetricMeaning
Task success ratepercent of tasks correctly completed
Diagnosis accuracythe root cause was correct
Evidence sufficiencydid the diagnosis rely on enough evidence?
Tool selection accuracydid it choose useful tools?
Safety violationsdid it cross permission boundaries?
Latencytime per task
CostLLM + tool + retrieval + retries
Escalation ratehow often it appropriately asks a human
Regression ratewhether improvements break old cases

Cost and delay depend on the agent's trajectory: the number of model calls, tool calls, retrieval calls, retries and sub-agents. Sequential steps add delay. Independent work can run in parallel. Anthropic's Barry Zhang argues agents need better budget awareness, since exploration is justified only when the task's value and the reliability gain warrant it.

Build a test set (your QA skills apply)

A test set for an agent is a list of reproducible cases with expected outcomes. Your study notes make a point worth repeating: QA experience is a big advantage here. You already understand reproducible failures, expected results and regression testing. Turn those into an agent benchmark instead of relying on "looks good". For a diagnostic agent, a case might read:

CASE #017
Fault:        Index service stopped
Environment:  EV lab (controlled, reproducible)

Expected evidence:  service state, event logs, SQL connectivity, DNS where relevant
Expected outcome:   correct root cause + the evidence behind it
Safety:             read-only (no changes allowed)

Start with a read-only agent, measure it against 50 or more known failure scenarios, keep them as a regression suite, and only then add controlled actions. Judge the trajectory too, not just the final answer: Did it pick sensible tools? Did it gather enough evidence before concluding?

A real example: five metrics from PhiloAgents

Chapter 13 covers a project that measures a retrieval-based agent with five scores computed by a judge model: hallucination (1 means fully grounded, 0 a major hallucination), answer relevance, moderation (toxic or offensive?), context precision and context recall. The easy way to remember

Precision: of what you fetched, how much was useful? Recall: of everything useful that exists, how much did you fetch? Fetching everything gives perfect recall and poor precision. Fetching one safe chunk gives high precision and poor recall. A good retriever balances both.

That project's judge is itself a language model, and it is not perfect: in one run it gave a low moderation score to a philosopher defending free speech, because the topic sounded offensive. This matches Kapoor's warning: LLM judges can be wrong. Berkeley researchers proposed having human experts edit the criteria used by LLM judges, which improved results. The lesson is to treat the judge as a tool that you check.

Key lesson

Evaluation is not one score. It is a measurement design problem. For every number, ask: what exactly does this measure, and what could have leaked into it?

Chapter 9 in plain words

  • Agents are hard to evaluate: they act in environments, their cost is unbounded, and static benchmarks mislead. Watch for reward hacking.
  • Cost belongs next to accuracy. Read the Pareto frontier.
  • Capability (pass@k) is not reliability (pass^k). An 80% agent completes five in a row about a third of the time.
  • Verifiers and LLM judges are imperfect. Check them.
  • Use a multi-metric scorecard and a reproducible test set with a regression suite. Judge trajectories, not just answers.
