## 1. Why this happens after you shipped

The image **passed its scans** and **a new vulnerability appeared the next week**. That is normal: **vulnerabilities are discovered continuously**, the code did not change but **knowledge about it did**. So there are two kinds of control:

- **Before deploy:** do not ship **known** problems (scanning gates).
- **After deploy:** **keep checking what is running** against new advisories, and be able to answer "**where is this package running?**" in minutes (**SBOM inventory**).

## 2. The response, in order

| Step | Question | Actions |
|---|---|---|
| **1. Assess** | How bad is it **for us**? | read the advisory; **severity (CVSS)**; is it **exploited in the wild** (known-exploited lists, EPSS probability)? Is the **vulnerable code reachable** in our usage? Is the service **internet-facing**? Does it hold **sensitive data or credentials**? |
| **2. Inventory** | **What is affected?** | from **SBOMs**, list **every image, version and running workload** with the package; owners; environments |
| **3. Contain** | Reduce exposure **now** | a **WAF/virtual patch** rule, a **network policy** or removing public exposure, disabling the feature (flag), scaling to zero a non-critical workload, tightening **egress** (blocks data exfiltration), rotating credentials the app could reach |
| **4. Patch** | Remove the cause | bump the dependency or **base image**, **rebuild**, test, ship through the **normal pipeline** (use an **expedited path**, not a bypass); if no fix exists, **mitigate and accept with an expiry** |
| **5. Verify** | Is it gone? | **re-scan the new image** and the **running pods** (by digest); check **old images are removed** or blocked from running; check logs for **signs of exploitation** |
| **6. Communicate** | Who must know? | security, owners, leadership, customers/regulators if exposure is plausible; a **timeline** |
| **7. Learn** | Make it faster next time | blameless review: detection time, inventory time, patch time; fix the **pipeline gap** (section 6) |

If there is **evidence of exploitation**, switch to **incident response** (Q9 in the senior track): preserve evidence, contain, rotate secrets, investigate lateral movement.

## 3. An SBOM, and matching it to advisories

An **SBOM (software bill of materials)** lists the **components inside an artefact** (the base image's OS packages and your language dependencies, with versions), generated at **build time** and stored with the image. It makes step 2 a **query** instead of a hunt. In practice a tool such as **Syft** generates it (formats **SPDX** or **CycloneDX**) and **Trivy or Grype** match it against vulnerability databases. We build a miniature of both so you can see the logic.

```run
mkdir -p ~/s8/images/web ~/s8/images/worker ~/s8/images/batch && cd ~/s8
# the "SBOM" baked into each image (normally generated by a tool such as Syft)
cat > images/web/sbom.txt <<'EOF'
libparse==2.3.0
httpkit==5.1.2
imgtool==1.8.0
EOF
cat > images/worker/sbom.txt <<'EOF'
libparse==2.4.1
queuelib==3.0.0
EOF
cat > images/batch/sbom.txt <<'EOF'
libparse==2.2.9
reportgen==0.9.0
EOF
# INVENTED advisories (not real CVEs)
cat > advisories.json <<'EOF'
[
 {"id": "ADV-2026-001", "package": "libparse", "fixed_in": "2.4.1", "severity": "critical", "exploited_in_wild": true,  "needs_feature": "xml-import"},
 {"id": "ADV-2026-002", "package": "imgtool",  "fixed_in": "1.9.0", "severity": "high",     "exploited_in_wild": false, "needs_feature": null},
 {"id": "ADV-2026-003", "package": "httpkit",  "fixed_in": null,    "severity": "medium",   "exploited_in_wild": false, "needs_feature": null}
]
EOF
cat > match.py <<'PY'
import json, glob, os

def ver(s): return tuple(int(x) for x in s.split("."))
advisories = json.load(open("advisories.json"))
SEVERITY = {"critical": 4, "high": 3, "medium": 2, "low": 1}

for sbom in sorted(glob.glob("images/*/sbom.txt")):
    image = os.path.basename(os.path.dirname(sbom))
    print(f"\nimage {image}:")
    found = False
    for line in open(sbom).read().split():
        pkg, v = line.split("==")
        for a in advisories:
            if a["package"] == pkg and (a["fixed_in"] is None or ver(v) < ver(a["fixed_in"])):
                found = True
                fix = f"upgrade to {a['fixed_in']}" if a["fixed_in"] else "NO FIX AVAILABLE: mitigate"
                print(f"  {a['id']}  {pkg} {v}  [{a['severity']}{', EXPLOITED IN THE WILD' if a['exploited_in_wild'] else ''}]  {fix}")
    if not found: print("  no known vulnerabilities")
PY
python3 match.py
```

**What you see:** `web` and `batch` contain the vulnerable `libparse`; `worker` already has the fixed version; `web` also has a **medium issue with no fix**, which needs mitigation rather than an upgrade. An SBOM turns "are we affected?" into a **file search**.

## 4. Where is it running? Inventory on the cluster

The images are only half of the answer: **which workloads, in which environments, run them?** Deploy three workloads that carry their image's SBOM as an annotation (in practice you would query an **SBOM store** or use the **running image digest** to look it up) and compute the **blast radius**:

```run
cd ~/s8
for img in web worker batch; do
kubectl apply -f - > /dev/null <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: $img
  labels: {app: $img, exposure: $( [ $img = web ] && echo internet || echo internal )}
spec:
  replicas: 2
  selector: {matchLabels: {app: $img}}
  template:
    metadata:
      labels: {app: $img, exposure: $( [ $img = web ] && echo internet || echo internal )}
      annotations:
        sbom/components: "$(tr '\n' ',' < images/$img/sbom.txt)"
    spec:
      containers: [{name: c, image: busybox:1.36, command: [sleep, "3600"]}]
EOF
done
kubectl rollout status deploy/web --timeout=90s > /dev/null
cat > inventory.py <<'PY'
import json, subprocess
def ver(s): return tuple(int(x) for x in s.split("."))
adv = json.load(open("advisories.json"))
pods = json.loads(subprocess.check_output(["kubectl", "get", "pods", "-o", "json"]))["items"]
by_app = {}
for p in pods:
    app = p["metadata"]["labels"].get("app")
    if not app or "sbom/components" not in p["metadata"].get("annotations", {}): continue
    by_app.setdefault(app, {"pods": 0, "components": p["metadata"]["annotations"]["sbom/components"], "exposure": p["metadata"]["labels"]["exposure"]})
    by_app[app]["pods"] += 1
print(f"{'workload':10} {'pods':>4} {'exposure':>9}  affected by")
for app, info in sorted(by_app.items()):
    hits = []
    for comp in filter(None, info["components"].split(",")):
        pkg, v = comp.split("==")
        for a in adv:
            if a["package"] == pkg and (a["fixed_in"] is None or ver(v) < ver(a["fixed_in"])): hits.append(a["id"])
    print(f"{app:10} {info['pods']:4} {info['exposure']:>9}  {', '.join(hits) or '-'}")
PY
python3 inventory.py
```

**What you see:** the **running workloads** that include a vulnerable component, how many pods, and whether they are **internet-facing**: the inputs for prioritising. (In a real estate, add environments, clusters, owners and versions, from a store such as a software-composition platform or a query over **registry metadata plus running image digests**.)

### Prioritise by risk, not by CVSS alone

Raw severity ranks everything "critical". Combine:

| Factor | Higher risk when |
|---|---|
| **Severity** (CVSS) | critical/high |
| **Exploited in the wild** or high EPSS | a public exploit exists |
| **Exposure** | internet-facing, or reachable from untrusted input |
| **Reachability** | your code calls the vulnerable function / enables the feature |
| **Data and privilege** | the workload holds secrets, PII, or powerful credentials |
| **Compensating controls** | a WAF rule, a network policy, a read-only filesystem lessen it |

```run
cd ~/s8
cat > risk.py <<'PY'
workloads = [
    # name, severity(1-4), exploited, exposure(internet=3, partner=2, internal=1), feature_enabled, holds_secrets
    ("web (ADV-2026-001)",    4, True,  3, True,  True),
    ("batch (ADV-2026-001)",  4, True,  1, False, False),
    ("web (ADV-2026-003)",    2, False, 3, True,  True),
]
def risk(sev, exploited, exposure, feature, secrets):
    score = sev * (3 if exploited else 1) * exposure * (1 if feature else 0.2) * (1.5 if secrets else 1)
    return score
print(f"{'workload':24} {'risk score':>10}  action")
for w in sorted(workloads, key=lambda w: -risk(*w[1:])):
    r = risk(*w[1:])
    action = "PATCH NOW + contain" if r >= 30 else ("patch this sprint" if r >= 8 else "track, patch with next release")
    print(f"{w[0]:24} {r:10.1f}  {action}")
PY
python3 risk.py
```

**What you see:** the internet-facing, exploited, secret-holding service is **top priority**; the same advisory in an internal batch job with the vulnerable feature **disabled** is far lower. (The weights are illustrative; the point is to make the reasoning **explicit and repeatable**.)

## 5. Fixing, and shipping the fix safely

- **Rebuild, do not patch in place:** change the dependency or **base image**, rebuild **from scratch**, rescan, and deploy the **new digest** through the pipeline. Containers are **immutable**; never `apt upgrade` inside a running pod.
- **Update the base image, not just your dependency**: many findings sit in the **OS layer**. Prefer **minimal bases** (distroless, Alpine, "slim", or scratch for static binaries): fewer packages, fewer vulnerabilities, smaller attack surface.
- **Fast path, not bypass:** a high-severity fix should flow through the same pipeline (tests, scans, signing, progressive rollout) with **priority** and **pre-approved** reviewers; skipping controls is how the second incident starts.
- **No fix available?** Mitigate (disable the feature, patch the call site, add input validation, WAF rule, remove the dependency), record an **accepted risk with an expiry**, and watch the advisory.
- **Verify:** rescan the **deployed digest**, confirm **no pods run the old digest** (use the inventory query), block the old digest from being pulled (admission policy) and **delete old images** from registries or mark them quarantined.

## 6. Securing the pipeline (so the next one is cheaper)

| Stage | Control | Purpose |
|---|---|---|
| **Source** | protected branches, **code review**, signed commits, **secret scanning**, **dependency review** on PRs | stop bad changes and leaked credentials early |
| **Dependencies** | **lock files with hashes** (for example `pip install --require-hashes`, npm lockfiles), a **private proxy/mirror** with allow-lists, **pin versions**, automated update PRs (**Renovate/Dependabot**) | reproducible builds, resist typosquatting and malicious updates |
| **Build** | **ephemeral, isolated runners**; least-privilege, **short-lived credentials (OIDC)** instead of long-lived secrets; **build from clean checkouts**; **pin base images by digest** | contain a compromised build |
| **Scan** | **SCA** (dependencies), **image scan** (OS and libraries), **SAST**, **IaC scan**, **secret scan**; **fail on critical/high with a fix** and an **expiring exception** process | do not ship known problems |
| **Artefact** | generate an **SBOM**, **sign the image** (cosign/Notary), attach **provenance** (who built what, from which commit; **SLSA** levels) | prove integrity and enable inventory |
| **Registry** | **continuous rescanning** of stored images, immutable tags, retention rules, access control | catch **new** advisories on old images |
| **Deploy** | **admission policy** (Kyverno, OPA Gatekeeper, a cloud policy): only **signed** images from **approved registries**, **no critical vulnerabilities**, **non-root**, no privileged pods, resource limits | enforce at the cluster door |
| **Runtime** | read-only root filesystem, **drop capabilities**, seccomp, **network policies and restricted egress**, runtime detection (Falco), least-privilege service accounts | limit what an exploit can do |
| **Operate** | inventory dashboards, alerting on **new criticals in production**, patch **SLAs** by severity, a **tested emergency-patch runbook** | detect and respond fast |

### Signing and verifying an image digest (real, with OpenSSL)

The idea behind **cosign** is a **digital signature over the image digest**, verified before running. The same mechanics with OpenSSL:

```run
cd ~/s8
openssl genrsa -out signer.key 2048 2> /dev/null
openssl rsa -in signer.key -pubout -out signer.pub 2> /dev/null
DIGEST="sha256:$(printf 'web-image-build-1042' | sha256sum | cut -d' ' -f1)"
echo "image digest to sign: $DIGEST"
printf '%s' "$DIGEST" | openssl dgst -sha256 -sign signer.key -out digest.sig
echo "--- verify the genuine digest:"
printf '%s' "$DIGEST" | openssl dgst -sha256 -verify signer.pub -signature digest.sig
echo "--- verify a tampered digest (someone swapped the image):"
printf "%s" "sha256:deadbeef" | openssl dgst -sha256 -verify signer.pub -signature digest.sig 2> /dev/null || true
```

**What you see:** the genuine digest verifies; a **swapped image fails**. An **admission controller** does exactly this check for every pod, refusing images that are unsigned or signed by the wrong identity. (Real tools use **keyless signing** tied to the CI identity and record signatures in a transparency log.)

```yaml:policy
# Example, not run here: an admission policy that only allows signed images from the approved registry
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: {name: require-signed-images}
spec:
  validationFailureAction: Enforce
  rules:
  - name: verify-signature
    match: {any: [{resources: {kinds: [Pod]}}]}
    verifyImages:
    - imageReferences: ["registry.example.com/*"]
      attestors: [{entries: [{keyless: {subject: "https://github.com/acme/*", issuer: "https://token.actions.githubusercontent.com"}}]}]
```

### Hardening the image itself (real)

```run
cd ~/s8
mkdir -p hardened && cd hardened
cat > Dockerfile <<'EOF'
FROM busybox:latest
COPY app.sh /app/app.sh
RUN chmod 555 /app/app.sh && adduser -D -u 10001 appuser
USER 10001
ENTRYPOINT ["/app/app.sh"]
EOF
printf '#!/bin/sh\necho "running as uid $(id -u); trying to write to /etc:"; touch /etc/x 2>&1 | head -1\n' > app.sh
docker build -q -t s8-hardened:1 . > /dev/null
echo "--- default run:"
docker run --rm s8-hardened:1
echo "--- hardened run (read-only filesystem, no capabilities, no new privileges):"
docker run --rm --read-only --cap-drop=ALL --security-opt no-new-privileges s8-hardened:1
```

**What you see:** the container runs as **uid 10001, not root**; it cannot write to system paths; with a **read-only filesystem and no capabilities** even more is denied. This does not remove a vulnerability, but it shrinks what an attacker can do **after** exploiting one.

## 7. The answer an interviewer expects

1. **Stay calm and structured:** assess → inventory → contain → patch → verify → communicate → learn.
2. **Assess in context:** severity **and** exploitability, exposure, reachability, data sensitivity (not just the CVSS number).
3. **Inventory fast** from **SBOMs** and running digests: which images, which workloads, which environments, which owners.
4. **Contain while patching:** WAF/virtual patch, network policy and egress restriction, disable the feature, rotate credentials if exploitation is possible.
5. **Patch properly:** rebuild with the updated dependency or base image, test, scan, sign, deploy through the pipeline (expedited, not bypassed), verify by digest, retire old images.
6. **Harden the pipeline:** gates, SBOM and signing, provenance, admission policy, continuous registry scanning, automated dependency updates, secure CI (least privilege, ephemeral runners, pinned digests).
7. **Measure:** time to detect, to inventory, to patch; track against **SLAs by severity**.

A spoken version: *"First I'd assess how serious it is for us, whether it's exploited, whether our code reaches it and whether the service is exposed, and in parallel query our SBOM inventory to see every image and workload that includes it. I'd contain with a WAF rule or by disabling the feature and restricting egress, then rebuild the image with the fixed dependency or base image, scan, sign and roll it out through the pipeline with a fast path, and verify that no pod still runs the old digest. Afterwards I'd close the gaps: SBOM generation, signed images enforced by admission policy, continuous rescanning of what's in production, automated dependency updates and patch SLAs."*

:::warn Common mistakes
- **Treating "passed the scan" as "safe forever."**
- **Ranking only by CVSS** and ignoring exposure and exploitability.
- **Patching a running container** or skipping the pipeline "just this once".
- **Updating the dependency but not the base image** (or the reverse).
- **No inventory**: you cannot answer "where is it running?".
- **Failing builds on every low finding**: teams learn to ignore or bypass the gate. Gate on **actionable** severities with **expiring exceptions**.
- **Ignoring the runtime**: root containers, writable filesystems and open egress turn a bug into a breach.
:::

## 8. Follow-up questions to expect

- **"How do you handle a vulnerability with no fix?"** Mitigate (feature off, WAF, input validation, isolate), accept with an owner and an expiry, monitor for a patch, consider replacing the component.
- **"What is a supply chain attack and how does this pipeline help?"** Compromise of a dependency, build system or registry; pinning with hashes, private mirrors, signed artefacts and provenance, ephemeral isolated builds, least-privilege credentials.
- **"SAST vs SCA vs DAST?"** SAST analyses **your source**, SCA checks **third-party dependencies**, DAST tests the **running application** from outside.
- **"How often should you rescan?"** Continuously for production (new advisories appear daily), at every build, and on a schedule for registries.
- **"What if the vulnerable image is in 200 services?"** Central base images updated once and rebuilt automatically; automated PRs to all repos; dashboards by owner; patch SLAs.

:::recap
- New vulnerabilities appear **after** deployment; you need **gates before deploy** and **continuous checking after**.
- Respond: **assess (in context) → inventory (SBOM) → contain → patch (rebuild, expedited pipeline) → verify by digest → communicate → learn**.
- **Prioritise by risk**: severity, exploitability, exposure, reachability, data, compensating controls.
- **Secure the pipeline**: pinned and hashed dependencies, scanning gates with exceptions, **SBOM, signing, provenance**, admission policy, registry rescans, least-privilege ephemeral CI.
- **Harden images** (minimal, non-root, read-only) to limit what an exploit achieves.
:::
