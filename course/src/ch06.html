Chapter 6

Fixing a model's weaknesses

By the end of this chapter you can explain:
  • five common weaknesses of language models
  • how retrieval-augmented generation (RAG) works, step by step, and where it breaks
  • how tool use (function calling) lets a model act on the world, and who really does the calling

Five weaknesses

Even a strong model has limits. Knowing them tells you why the techniques in this chapter exist.

  1. Hallucination. It can state false things confidently, especially in maths and specific facts.
  2. Knowledge cut-off. Its training data stops at some date. It has not seen recent news.
  3. No sources. It can answer, but it cannot tell you which document the answer came from.
  4. No private data. It was trained on public text. It has never seen your company's documents.
  5. Limited context. It can only read so much text at once. Longer inputs cost more and respond slower.

Fix 1: Retrieval-Augmented Generation (RAG)

The idea is simple. Do not ask the model to remember. Look up the relevant pages first, then hand them to the model with the question. It is an open-book exam instead of a closed-book exam. You already used the prompt side of this in Chapter 5, habit 3. RAG adds the automatic "look up" step.

RAG step by step Example: a company help desk
Words you will hear

Chunk: a small piece of a document, like one paragraph. Embedding: a list of numbers that represents the meaning of a piece of text, so texts with similar meaning get similar numbers (Chapter 2). Vector database: a store that can quickly find the stored chunks whose numbers are closest to a question's numbers. Top-k: the k best matches, for example the best 3. Reranking: a second pass that re-orders the candidates so the most useful come first.

Each design choice is a question

ComponentThe question it answers
ChunkingWhat unit of text should be retrieved?
EmbeddingHow do we represent its meaning as numbers?
Vector indexHow do we find similar candidates quickly?
Top-kHow many candidates should we fetch?
RerankingWhich of the candidates are most useful?
Context assemblyHow do we present the evidence to the model?

What just happened?

"How long until I get my money back?" returns nothing useful, even though the refund-timeline chunk is exactly the answer. The question says "money back" and the chunk says "refunds". Keyword search needs shared words. Embeddings fix this because "money back" and "refund" land close together on the meaning map from Chapter 2. Real systems therefore often combine both: a hybrid of keyword and vector search. This is also a lesson about RAG itself: RAG is not a guarantee of truth. Bad retrieval can supply irrelevant or contradictory evidence, and the model can still misread what it is given.

What RAG fixes

  • Less hallucination, because the answer comes from supplied text.
  • Citations are possible, because you know which chunk was used.
  • Fresh information and your private documents become usable.
  • You only send a few relevant chunks, so the context stays short.

There are other ways to retrieve. You can search the web instead of your own files. You can turn your documents into a knowledge graph (things and the relationships between them), which is called graph RAG. The common pattern is the same: find relevant material, put it in the prompt. Chapter 13 shows a real project that builds its long-term memory exactly this way.

Fix 2: Tool use (function calling)

A language model takes text in and gives text out. On its own it cannot check the weather, send an email or do a long calculation reliably. Tool use gives it hands.

You tell the model, in the prompt, which tools exist and the exact format to use when it wants one. When the model decides a tool is needed, it writes a request in that format. Your software (not the model) notices the request, runs the real function, and passes the result back to the model. Then the model writes the final answer for the user. Step through it:

Tool use step by step Question: "What's the weather in San Francisco?"
Common mistake

Beginners think the model itself calls the weather service. It does not. The model only writes text that asks for the call. Your own program does the calling. The model proposes. Your software executes. This split matters a lot for safety, because your software is where you validate the request, check permissions and write an audit log.

The same idea covers writing code. The model can write a small program to do a calculation or draw a chart, and your software runs it in a protected area called a sandbox, then returns the output to the model.

A famous demo

In his intro talk, Andrej Karpathy asks ChatGPT for a company's funding rounds in a table. The model searches the web and builds the table. Asked to estimate the missing values from the ratios, it uses a calculator, because models are not reliable at arithmetic "in their head". Asked for a chart with a trend line, it writes plotting code and runs it. Finally it calls an image generator. Four tools, one conversation. Humans solve problems the same way: we do not do everything in our heads, we use tools.

Models as the "kernel" of a new kind of computer

Karpathy offers a picture worth remembering. An LLM is less a chatbot than the kernel of an emerging operating system. It reads and writes text, browses the web or your files (retrieval), uses software like a calculator or Python, sees and generates images, hears and speaks, and could eventually think longer and be customised for tasks. The context window is its working memory (like RAM), and the kernel decides what to page in and out. Even the ecosystem looks familiar: a few closed systems (like Windows and macOS) and a growing open-source family (like Linux). You will see in the next chapters how an agent is what you get when you run this "operating system" in a loop.

Where this leads

Put the pieces together. A model that can retrieve information, use tools, and look at the results and decide what to do next is no longer just answering. It is working on a task. That is the starting point for the next chapter.

Try it yourself (optional, runs offline)

Here is the mini search engine from Lab 2 in about 30 lines of Python. It is a complete retrieval step. Add a document, ask the "money back" question, and then try improving it, for example by adding a small table of synonyms. That is a first taste of why embeddings exist. The file is also saved as course/examples/mini_rag.py.

import math, re
from collections import Counter

DOCS = {
    "Returns policy": "Items can be returned within 30 days of delivery for a full refund if unused.",
    "Clothing exceptions": "Jackets can be returned within 30 days if unworn and with tags attached.",
    "Refund timeline": "Refunds are issued to the original payment method within 5 to 7 business days.",
    "Shipping options": "Standard shipping takes 3 to 5 business days. Orders over 50 dollars ship free.",
    "Password reset": "Choose forgot password on the sign in page. We email a reset link.",
}
STOP = {"a","an","the","of","to","in","on","for","and","or","is","are","be","can","i","my","if","how","what","with"}

def stem(word):
    return re.sub(r"(ing|ed|es|s)$", "", word)      # very crude: returned -> return, jackets -> jacket

def words(text):
    return [stem(w) for w in re.findall(r"[a-z0-9]+", text.lower()) if w not in STOP]

def tfidf(tokens, df, n):
    tf = Counter(tokens)
    return {w: c * (math.log((n + 1) / (df.get(w, 0) + 1)) + 1) for w, c in tf.items()}

def cosine(a, b):
    dot = sum(v * b.get(w, 0) for w, v in a.items())
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return dot / (na * nb) if na and nb else 0.0

tokenised = {t: words(t + " " + body) for t, body in DOCS.items()}
df = Counter(w for toks in tokenised.values() for w in set(toks))
vectors = {t: tfidf(toks, df, len(DOCS)) for t, toks in tokenised.items()}

def retrieve(question, k=2):
    q = tfidf(words(question), df, len(DOCS))
    scored = sorted(((cosine(q, v), t) for t, v in vectors.items()), reverse=True)
    return scored[:k]

def build_prompt(question, k=2):
    chunks = [f"[{t}] {DOCS[t]}" for score, t in retrieve(question, k) if score > 0]
    return ("Answer using only the text below. If the answer is not there, say you cannot find it.\n\n"
            + "\n".join(chunks) + f"\n\nQuestion: {question}")

print(build_prompt("Can I return a jacket I bought three weeks ago?"))
print()
print(build_prompt("How long until I get my money back?"))   # keyword search misses this one

Chapter 6 in plain words

  • Models hallucinate, go out of date, cite nothing, miss private data and have limited reading room.
  • RAG looks up relevant chunks and puts them into the prompt. Chunking, embeddings, top-k and reranking are the design choices. RAG is not a guarantee of truth.
  • Tool use lets the model ask your software to run functions and return results. The model proposes. Your software executes.
  • Combine retrieval, tools and a loop, and you are close to an agent.
